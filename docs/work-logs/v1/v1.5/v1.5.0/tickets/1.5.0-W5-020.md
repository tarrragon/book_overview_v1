## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

現有框架中存在三層寫入模式：

**第 1 層（已制式化）**：frontmatter 欄位由 CLI 命令寫入
- set-who/what/when/where/why/how、set-acceptance、set-priority、claim/complete
- 格式錯誤率：趨近零（CLI 強制正確格式）

**第 2 層（半制式化）**：body 章節由 append-log 寫入自由文字
- Problem Analysis、Solution、Test Results、Completion Info、Exit Status
- 章節存在由 CLI 保證（create 時產生 placeholder），內容由 agent 自由撰寫
- 格式錯誤率：中（依 agent prompt 品質波動）

**第 3 層（有 schema 但自由撰寫）**：body 內的結構化子欄位
- multi\_view\_status（Solution 內，flat key-value + 子欄位）
- Exit Status（YAML block，7 欄位）
- Completion Info（3 行固定結構）
- 格式錯誤率：高（agent 不知正確格式，hook 只能事後警告）

核心矛盾：第 3 層有確定性 schema，但寫入方式與第 2 層（自由文字）相同。agent 需同時處理「語意內容」和「格式結構」——而格式結構是確定性的，應由工具承擔。

### 影響範圍

- ticket CLI 的 append-log / set-* 命令族
- acceptance-gate-hook 的各 checker
- 所有 agent 寫 ticket body 的流程

### 相關 Error Pattern

- W5-018：multi\_view\_status 格式錯誤（heading vs flat）
- PC-117 / W17-111：nested YAML 結構誤用
- opinionated-default-design 原則主張 3（AI agent 場景加倍）

## 重現實驗結果
### 實驗方法

盤點框架內所有「有 schema 約束的寫入點」，分類為已制式化 vs 未制式化。

### 實驗執行

| 寫入點 | Schema | 制式化？ | 錯誤頻率 |
|-------|--------|---------|---------|
| 5W1H frontmatter | YAML 鍵值 | 是（set-who/what/...） | 趨近零 |
| acceptance | 勾選索引 | 是（set-acceptance） | 趨近零 |
| status | 狀態機 | 是（claim/complete） | 趨近零 |
| priority | P0-P3 枚舉 | 是（set-priority） | 趨近零 |
| multi\_view\_status | flat kv + 子欄位 | 否（append-log 自由文字） | 高（W5-018 實證） |
| Exit Status | YAML block 7 欄位 | 否 | 中（常漏欄位） |
| Completion Info | 3 行固定格式 | 否 | 中（格式不一） |
| 自檢結果 | checklist | 否 | 低（格式簡單） |

### 實驗發現

**已驗證事實**：
1. 已制式化（CLI 命令）的寫入點格式錯誤率趨近零
2. 未制式化但有 schema 的寫入點格式錯誤率中-高
3. 兩者差異的唯一變數是「誰負責格式結構」——CLI vs agent
4. 現有框架已有成功模式（set-* 命令族），可直接推廣
5. 第 3 層場景至少 3 個（multi\_view\_status / Exit Status / Completion Info）可 CLI 化

2. **規則**：`.claude/rules/core/structured-content-generation.md`
