## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

error-patterns 已達 348 檔（PC 201 / IMP 90 / ARCH 29 / DOC 11 / test 9 / CQ 6 / process 1），共 33,171 行，平均每檔 96 行。現有查詢手段：

1. **grep + 同義詞展開**（SKILL.md 定義）：10ms 內完成 348 檔全掃，效能不是問題
2. **同義詞家族表**：僅 5 個家族（confabulation / scope creep / silent failure / stale state / tool selection bias），手動維護
3. **LLM 讀取 grep 結果**：廣泛關鍵字雜訊高（如「dispatch」命中 129/348 = 37%）

### 影響範圍

- `.claude/error-patterns/` 全部 348 檔
- `.claude/skills/error-pattern/SKILL.md` 查詢流程
- PM 每個 ticket 開始前的 error-pattern 查詢品質

### 相關 Error Pattern

- PC-166：confabulation（查詢結果可能被 LLM 虛構）
- PC-162：grep 分類高估重複工作量（grep 命中是候選不是判決）
- framework issue #14：近似重複偵測需求

### 結構化查詢基礎

348 檔中僅 107 個（31%）有 YAML frontmatter（id/title/category/severity/source_case/created），其餘用 inline markdown 格式記錄元資料。

## 重現實驗結果
### 實驗方法

三種查詢手段對 348 檔 error-patterns 的搜尋能力實測：
1. grep + 同義詞展開（現有 SKILL.md 流程）
2. codebase-memory-mcp（search_code / search_graph / semantic_query）
3. codegraph（search_by_error / search_by_pattern）

使用兩組關鍵字：「confabulation 語意族」與「grep 分類高估」。

### 實驗執行

**grep baseline**：
- confabulation 家族（8 詞展開）→ 15 檔命中，10ms 完成
- 「dispatch」→ 129/348 命中（37% 雜訊率），10ms
- 「grep 分類 / overcounts / 高估」→ 5 檔命中

**codebase-memory-mcp**：
- search_code「confabulation」→ 0 命中
- search_graph semantic_query「confabulation」→ 10 筆全不相關（score 負值，全指向 src/ JS 函式）
- 根因：索引以程式碼符號為單位，.md 純文字檔不產生符號節點

**codegraph**：
- search_by_error「confabulation」→ 0 命中
- search_by_pattern「confabulation」→ 0 命中
- 根因：Tree-sitter 解析器針對程式碼檔，.md 不在解析範圍

### 實驗發現

**已驗證事實**：
1. 兩個 MCP 都是程式碼搜尋工具，對 .md 知識庫文件完全無覆蓋能力（0 命中 vs grep 15 命中）
2. grep 效能在 348 檔規模下無瓶頸（10ms）
3. grep 雜訊問題來自高頻詞命中率（37%），非效能問題
4. 同義詞表僅 5 家族，覆蓋不足（348 檔中涉及數十個概念）
5. frontmatter 覆蓋率僅 31%（107/347），結構化查詢基礎不足

**仍未驗證的假設**：
- 是否存在 LLM-native 的 .md 語意搜尋 MCP（如 RAG 類工具）可替代自建
- frontmatter 全量補齊的成本估算

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 方案比較

### 方案 A：維持現狀（grep + 同義詞展開 + LLM 讀結果）

| 維度 | 評估 |
|------|------|
| 查詢效能 | 10ms / 348 檔，無瓶頸 |
| 查詢精確度 | 高頻詞雜訊率 37%；同義詞表僅 5 家族，概念覆蓋不足 |
| 重複偵測 | 無（framework issue #14 仍 open） |
| confabulation 風險 | 中（LLM 讀大量 grep 結果時仍有虛構風險）|
| 開發成本 | 零 |
| 維護成本 | 同義詞表手動維護（低頻） |

### 方案 B：既有 MCP 整合（cbm + codegraph）

| 維度 | 評估 |
|------|------|
| 適用性 | **完全不適用**——兩者都是程式碼符號搜尋工具，.md 知識庫文件 0 命中 |
| 結論 | **淘汰** |

### 方案 C：自建 error-pattern CLI 查詢工具

| 維度 | 評估 |
|------|------|
| 可做什麼 | frontmatter 結構化查詢（by category/severity/date）、語意分群、近似重複偵測 |
| 前提條件 | frontmatter 覆蓋率需從 31% 提升至 >90%（需補齊 ~240 檔） |
| 開發成本 | CLI 本體約 1-2 個 IMP ticket；frontmatter 補齊約 3-5 個批量 DOC ticket |
| 維護成本 | 新增 error-pattern 時需維護 frontmatter（已有 add 流程強制） |
| 預期收益 | 結構化查詢降雜訊（by severity 篩選 high-only）；近似重複偵測解 issue #14 |

### 方案 D：增強現有 grep 流程（中間路線）

| 維度 | 評估 |
|------|------|
| 可做什麼 | 擴充同義詞家族表（5→15+）、query 結果加 frontmatter 摘要排序、category 篩選 |
| 前提條件 | 最小——在現有 SKILL.md 流程上漸進改良 |
| 開發成本 | 1 個 IMP ticket（改良 query 子命令） |
| 維護成本 | 同義詞表維護（與現狀同） |
| 預期收益 | 降雜訊（category 篩選）、改善排序（有 frontmatter 的優先顯示）|

### 結論與建議

**建議採方案 D（增強現有 grep 流程）為短期改善，保留方案 C 為長期方向。**

**理由**：

1. **方案 B 淘汰**：既有 MCP 對 .md 文件完全無效，此路不通
2. **方案 C 投入過高**：frontmatter 補齊 240 檔是大量機械工作，且現有 grep 效能無瓶頸——投入產出比不合理
3. **方案 D 最小可行**：在現有基礎上漸進改良，1 個 ticket 即可改善最大痛點（雜訊率）
4. **方案 A 可接受但有改善空間**：現狀能用，但 37% 雜訊率和 5 家族同義詞覆蓋是可量化的改善目標

**方案 D 具體改善項**：
- query 子命令支援 `--category PC/IMP/ARCH` 篩選（立即降雜訊）
- 同義詞家族從 5 擴充到 10-15（覆蓋高頻概念）
- 有 frontmatter 的結果優先顯示摘要（id/title/severity）
- query 結果加計數提示（「命中 N 檔，建議加 --category 篩選」）

**長期方向**：若 error-patterns 規模達 500+ 檔或跨專案共享需求增長，再評估方案 C。frontmatter 補齊可作為漸進式 DOC 任務，每版本補 20-30 檔。
