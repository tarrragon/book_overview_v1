## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

現行 `track_runqueue.py` 排序邏輯（L322-323, L420-422）為 `(_priority_rank(t), str(t.get("id", "")))`，僅依 priority → id 字串排序。缺少兩個維度：

1. **type 權重**：同 priority 的 ANA 與 IMP 排列無差異，PM 無法從 runqueue 輸出直覺判斷「先做分析再做實作」
2. **並行可行性**：runqueue 不標示哪些 ticket 可並行派發，PM 須人工逐一判斷 where.files 重疊性

### 影響範圍

- `.claude/skills/ticket/ticket_system/commands/track_runqueue.py` — list 和 DAG 兩處 sort key
- `.claude/pm-rules/decision-tree.md` — 若機制變更需同步路由描述

### 相關 Error Pattern

無直接對應 PC。本問題是 PM 效率缺口，非錯誤模式。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 四項分析結論

### AC-1：現行排序邏輯盤點與缺口分析

**現行邏輯**：`track_runqueue.py` 兩處排序（L322-323 list 視圖、L420-422 DAG 視圖）使用相同 sort key：

```python
key=lambda t: (_priority_rank(t), str(t.get("id", "")))
```

排序維度僅兩層：priority 數值（P0=0, P1=1, P2=2, P3=3, 未知=99）→ ticket ID 字串。

**缺口**：

| 缺口 | 影響 |
|------|------|
| 無 type 權重 | 同 priority 的 ANA 和 IMP 混排，PM 無法快速辨識「先分析後實作」的自然順序 |
| 無並行可行性標示 | PM 須人工比對 where.files 判斷哪些 ticket 可並行派發 |
| 無 created 排序 | 同 priority 同 type 的 ticket 依 ID 字串排序而非建立時間 |

### AC-2：type 權重排序方案評估

**方案：在 sort key 加入 type 權重作為第二維度**

建議 type 權重表：

| type | 權重 | 理由 |
|------|------|------|
| ANA | 0 | 分析結論影響實作方向，先做分析避免走錯路 |
| DOC | 1 | 文件常為分析落地或規格前置，優先級接近 ANA |
| IMP | 2 | 實作依賴分析結論，排在分析之後 |
| 未知 | 9 | 安全預設 |

修改後 sort key 變為：`(_priority_rank(t), _type_rank(t), str(t.get("id", "")))`

**邊界條件**：

- type 權重是 priority 內的次排序，不會讓 P2 ANA 排到 P0 IMP 前面
- 此排序為「建議順序」而非強制執行順序，PM 仍可依判斷調整
- 已有 blockedBy 依賴的 ticket 在 list 視圖中已被過濾（_is_unblocked_pending），type 排序不影響依賴邏輯

### AC-3：並行可行性提示方案評估

**結論：不建議在 runqueue 內建並行可行性自動分組**

理由：

1. **where.files 不充分**：並行可行性除檔案重疊外，還需判斷語意衝突（同模組不同檔案可能有隱性依賴），自動判斷 false negative 風險高
2. **PM 已有工具**：`parallel-dispatch.md` + `dispatch-gate.md` 提供並行派發 SOP，PM 在派發時判斷更精確
3. **投入產出比低**：自動分組需解析 where.files 交集、處理缺值情況、維護分組邏輯，但 PM 每次 runqueue 只看頂部數個 ticket，人工判斷成本低

**替代建議**：在 runqueue list 輸出中為 ticket 標示 type（已有 priority 標示），讓 PM 快速識別可並行的同 type 組。目前 list 輸出格式為 `[P1] ticket-id - title`，建議改為 `[P1|ANA] ticket-id - title`。

### AC-4：結論——機制變更（小幅）

**建議機制變更**（spawn 一個 IMP ticket）：

1. **新增 `_type_rank()` 函式**：type 權重對照表（ANA=0, DOC=1, IMP=2, 未知=9）
2. **修改兩處 sort key**：L322-323 和 L420-422 加入 type 權重作為第二維度
3. **修改 list 輸出格式**：在 priority 標籤旁顯示 type（如 `[P1|ANA]`）

不需修改 decision-tree.md（排序是工具行為變更，非決策路由變更）。

| 項目 | type | 內容 |
|------|------|------|
| runqueue type 權重排序 + type 標籤 | IMP | 修改 track_runqueue.py：新增 _type_rank()、修改兩處 sort key、修改 list 輸出格式加 type 標籤 |
