1. sync-claude-pull.py 已有 hook 權限還原機制——log 明示「已還原 28 個 hook 檔案的執行權限」，且新 pull 進來的 2 個 hook 檔（reference-stability-rule8-guard-hook.py、tests/test_version_tracking_consistency_guard_hook.py）正確以 100755 落地。

   - 需釐清 skills/ 下哪些 python 是「路徑執行」（需 +x）vs「被 import 的模組」（不需 +x），避免無差別加 +x 污染。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 三方案評估

### 方案 A：PostToolUse hook 對新寫入的 .py 自動 chmod +x

- 優點：即時修復，Write 工具產出後立刻對齊
- 缺點：(1) 過度涵蓋——skills/ 和 scripts/ 下的模組檔（__init__.py、cli.py）不需要 +x，無差別加 +x 語意污染；(2) 需區分「路徑執行」vs「被 import 的模組」，判斷規則複雜（shebang? settings.json 註冊? 目錄慣例?）；(3) PostToolUse hook 在每次 Write 觸發，效能開銷
- 結論：**不採用**——問題域（hooks/ 權限）已被方案 B 現有機制覆蓋；擴展到全 .claude/ 的收益不足以證成判斷複雜度

### 方案 B：hook-completeness-check 升級（評估現狀）

- 現狀已具備：_check_and_fix_permissions() 對 hooks/ 遞迴掃描並自動 chmod +x + 自動 commit（僅 mode-only 變更時）
- 覆蓋範圍：hooks/ 目錄（含子目錄如 acceptance_checkers/、lib/、tests/）
- 觸發時機：每次 SessionStart
- 實測：170 個 hooks/*.py 全部 100755，零殘留
- sync-pull 補強：sync-claude-pull.py 有獨立的 hook 權限還原機制
- 結論：**已足夠**——hooks/ 是唯一需要 +x 的 .py 集合（CC runtime 直接路徑執行），現有雙層機制（SessionStart + sync-pull）已完全覆蓋

### 方案 C：維持現狀僅文件提醒

- 已被方案 B 淘汰——方案 B 不是「僅文件提醒」，而是已實作的自動修復機制

### 結論

**選定方案 B（維持現狀，不需額外 IMP）**。

判準依據（opinionated-default-design 方法論）：
- 主張 1（預設行為 > 文件規範）：hook-completeness-check.py 的自動修復已是「工具預設行為」，不依賴文件提醒
- 主張 2（有預設值就表達）：自動修復 + 自動 commit 即工具表達的 opinion
- 主張 3（AI agent 場景加倍）：SessionStart 自動觸發，不依賴 agent 記憶
- 主張 4（清理路徑主動掃描）：已實作遞迴掃描 + 報告

W5-024 觀察到的 3 檔殘留（install-skill-clis.py + spawn_request_checker.py + 其 test）不是機制缺陷——是 hook-completeness-check 修復後、其他變更混入工作區導致自動 commit 安全閥跳過（changed_paths != fixed_rel_set 保護），已在後續手動 commit 中修復。這是正確行為（防止夾帶無關變更）。

不建 IMP ticket。無需後續工作：現有 hook-completeness-check.py 已完全覆蓋 hooks/ 權限對齊需求，方案 B 結論為「維持現狀」。AC 第 2 項「若選 A/B 則 spawn」——方案 B 評估結果為「現有機制已足夠，不需升級」，故無 IMP 需建。
