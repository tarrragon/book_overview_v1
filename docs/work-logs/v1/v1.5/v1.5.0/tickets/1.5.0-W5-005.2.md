## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

- 身份晚綁定：who.current 預設 "pending"/"待派發"，綁定依賴 agent 自覺執行 claim --as（W2-018 提供機制但未強制）；2285 票普查中 17%（376/2190）completed 票身份從未回填（W5-005 F1a）。
- 派發時 PM 已知執行者身份（Agent tool 的 subagent_type 參數），但此資訊未落入 ticket，於派發到認領之間遺失。

### 影響範圍

- `.claude/hooks/dispatch-record-hook.py` — PreToolUse(Agent) 既有 hook，擴充條件式身份綁定（無新 hook、無新註冊，避開 IMP-051）
- `.claude/references/agent-dispatch-template.md` — prompt 骨架補強制 claim --as 行
- `.claude/hooks/tests/` — 新增綁定邏輯測試
- `identity_guard.py` 零變更（TOFU 否決，見下）

### TOFU 對照方案評估（acceptance 2：否決，附理由）

方案定義：complete/check-acceptance --as X 遇無主態（who.current 為 pending/待派發/空）時視為首次認領，回填 who.current=X 並放行；已綁定態維持 deny。

**否決**，理由四點：

1. 職責違反：check_identity 契約為「純前置檢查，不寫入任何 ticket 狀態」（identity_guard.py docstring 明文）；TOFU 使 guard 變 writer，寫入點落在三個命令（complete/check-acceptance/set-acceptance）共用路徑，鎖時序複雜化。
2. 訊號遮蔽：complete 端回填會粉飾「17% 未回填」指標——派發端綁定失效時 TOFU 兜底，監測失真，無法區分「派發綁定成功」與「收尾補救」。
3. 威脅模型反向：PC-V1-002 防的是 generic agent 越權收尾；TOFU 合法化「任意 agent 對無主票自我指派」路徑。warn-only 過渡期無實質差異，但 W1-049 轉 deny 後 TOFU 成為越權後門。
4. 需求消失：派發端條件式綁定（採納案）使派發流程中的無主態結構性消失；殘餘無主場景（PM 前台代收尾）已有 PM 豁免（情境 2），TOFU 無服務對象。

### 採納方案：dispatch 條件式綁定（TOFU-at-dispatch）+ 模板對稱強制

- **A 機制層**：dispatch-record-hook.py 於 PreToolUse(Agent) 提取 prompt 首行 Ticket ID（PC-065 格式，regex 含子票後綴 `(?:\.\d+)*`）+ tool_input.subagent_type；經 `ticket track who` 讀取現值，僅無主態時 `ticket track set-who` 綁定。**已綁定態不覆蓋**——審查型派發（acceptance-auditor 對他人票）prompt 首行同樣含 Ticket ID，無條件綁定會 clobber 真執行者身份。subagent_type 缺省時跳過（無穩定身份可綁）。全失敗路徑 log warning 後放行（非阻擋 hook）。
- **B 文件層**：agent-dispatch-template.md 骨架補強制 `ticket track claim <id> --as <agent-name>` 行，作為 hook 失效時的 agent 端 fallback。
- 設計依據：opinionated-default-design 主張 1（預設行為 > 文件規範）與主張 3（AI agent 無跨 session 記憶，工具即時引導是唯一可靠防線）；讀寫皆走 ticket CLI 不直接 parse 檔案（W5-005 F3 寫入收斂方向 + F9 grep 消費者風險）。

### 相關 Error Pattern

PC-V1-002（generic agent 越權收尾）、PC-065（prompt 首行 Ticket ID）、PC-050（dispatch-active 記錄端缺失）、IMP-051（新 hook 須註冊——本案擴充既有已註冊 hook 迴避）、W2-018（claim --as 對稱機制）

### 實作內容（雙層防護）
