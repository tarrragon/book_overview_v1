## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

agent 執行 ticket 過程中發現應開新 ticket 的議題時，資訊流有三個缺口：

**缺口 1：無專屬結構化欄位**
- ANA ticket 有「Spawn 落地確認」表格慣例（在 Solution 內），但這是 ANA 專屬且為自由格式
- IMP/DOC ticket 無對應機制，agent 把 spawn 建議散落在 Solution/Completion Info/Execution Log
- PM 讀取時被其他分析內容稀釋，易漏

**缺口 2：結構不確定**
- 現有 spawn 建議格式不統一：有的寫表格、有的寫散文、有的只提一句
- spawn 建議需要的資訊量不小（what/why/suggested-type/suggested-priority/related-files），但沒有 schema 規範

**缺口 3：無 CLI 寫入命令**
- 依制式化方法論：有確定性 schema + 多寫入者（所有 agent）+ 歷史格式問題 → 應 CLI 化
- 現有 append-log 只能寫自由文字，無法強制 spawn 建議的結構

### 影響範圍

- ticket body schema（所有 type）
- CANONICAL\_BODY\_SECTIONS（可能新增 section）
- acceptance-gate-hook（偵測未處理的 spawn request）
- agent 執行流程（complete 前的回報 SOP）

### 現有機制盤點

| 機制 | 覆蓋場景 | 缺口 |
|------|---------|------|
| Solution 「Spawn 落地確認」 | ANA ticket 的分析結論 spawn | 僅 ANA；自由格式；agent 自己建表格 |
| spawned\_tickets frontmatter | PM 建 ticket 後的追蹤 | 只記已建立的 ticket，不記「建議建立」 |
| NeedsContext section | agent 回報資料缺口 | 語意不同——缺料 vs 建議開票 |
| Exit Status section | agent 結束狀態 | 語意不同——完成狀態 vs 建議開票 |

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 設計方案

**新增 body section：Spawn Requests**

在 CANONICAL\_BODY\_SECTIONS 新增第 10 個章節 `Spawn Requests`，位於 `Exit Status` 之後、`Completion Info` 之前。語意：**agent 建議 PM 開新 ticket 的結構化請求清單**。

#### Schema 設計

每個 spawn request 為一個結構化條目：

```
- what: <建議開票的目標描述>
  why: <發現此問題的原因/觸發情境>
  suggested_type: <IMP|ANA|DOC>
  suggested_priority: <P0|P1|P2>
  related_files: <相關檔案路徑，逗號分隔>
  context: <補充 context，可選>
```

#### CLI 命令設計

```bash
ticket track add-spawn-request <ticket-id> \
  --what "描述" \
  --why "原因" \
  --type IMP \
  --priority P2 \
  --files "path1,path2" \
  --context "補充說明"
```

CLI 行為：
1. 在 `## Spawn Requests` 章節追加一個結構化條目
2. 自動編號（SR-1, SR-2, ...）
3. auto-commit（與 append-log 同機制）
4. 驗證 suggested\_type 和 suggested\_priority 為合法枚舉值

#### acceptance-gate-hook 擴充

complete 時檢查：若 `Spawn Requests` 章節有條目，每個條目必須標記 `status: processed`（PM 已建 ticket）或 `status: dismissed`（PM 評估後決定不建）+ `reason`。未處理的 spawn request 阻擋 complete。

但注意：**這個 hook 檢查的是 PM 的處理動作，不是 agent 的**——agent 只負責寫 request，PM 負責處理。所以阻擋點應在 PM 完成驗收時（而非 agent complete 時）。

#### 與現有機制的關係

| 機制 | 語意 | 時機 | 執行者 |
|------|------|------|--------|
| Spawn Requests（新） | 建議開票（request） | agent 執行中發現問題 | agent |
| spawned\_tickets（現有） | 已建立的 ticket（fulfillment） | PM 建 ticket 後 | PM/CLI 自動 |
| Solution Spawn 落地確認（現有） | ANA 分析結論的 spawn 規劃 | ANA Solution 撰寫時 | agent（ANA 專屬） |

三者是 **request → fulfillment → verification** 三階段：
1. agent 寫 Spawn Request（request）
2. PM 讀取後建 ticket，CLI 自動填入 spawned\_tickets（fulfillment）
3. acceptance-gate-hook 驗證 spawned\_tickets 與 Spawn Requests 一致（verification）

ANA Solution 的 Spawn 落地確認維持不變——它是「分析結論的一部分」而非「執行中的發現」，語意不同。

### 結論

**採上述方案：新增 `Spawn Requests` body section + `add-spawn-request` CLI 命令。**

**理由**：
1. 填補現有 9 章節的語意缺口——「建議開票」是獨立語意，不應塞入其他章節
2. CLI 化符合制式化方法論——有確定性 schema + 多寫入者（所有 agent）
3. request → fulfillment → verification 三階段清晰分離職責
4. 向後相容——新增章節不破壞現有 ticket，未使用時章節為空或不出現

### Spawn 落地確認

| 項目 | 類型 | 是否需建 ticket |
|------|------|----------------|
| Spawn Requests section 實作（constants + create 模板 + append-log 白名單） | IMP | 是 |
| add-spawn-request CLI 命令實作 | IMP | 可併入上一項 |
| acceptance-gate-hook Spawn Requests 處理狀態檢查 | IMP | 是——獨立 ticket |
| ticket-body-schema.md 更新 | DOC | 可併入 section 實作 ticket |

評估後決定：合併為 1 個 IMP ticket（section + CLI + schema 文件）+ 1 個 IMP ticket（hook 檢查）。
