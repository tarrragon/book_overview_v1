## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

agent 執行 ticket 過程中發現應開新 ticket 的議題時，資訊流有三個缺口：

**缺口 1：無專屬結構化欄位**
- ANA ticket 有「Spawn 落地確認」表格慣例（在 Solution 內），但這是 ANA 專屬且為自由格式
- IMP/DOC ticket 無對應機制，agent 把 spawn 建議散落在 Solution/Completion Info/Execution Log
- PM 讀取時被其他分析內容稀釋，易漏

**缺口 2：結構不確定**
- 現有 spawn 建議格式不統一：有的寫表格、有的寫散文、有的只提一句
- spawn 建議需要的資訊量不小（what/why/suggested-type/suggested-priority/related-files），但沒有 schema 規範

**缺口 3：無 CLI 寫入命令**
- 依制式化方法論：有確定性 schema + 多寫入者（所有 agent）+ 歷史格式問題 → 應 CLI 化
- 現有 append-log 只能寫自由文字，無法強制 spawn 建議的結構

### 影響範圍

- ticket body schema（所有 type）
- CANONICAL\_BODY\_SECTIONS（可能新增 section）
- acceptance-gate-hook（偵測未處理的 spawn request）
- agent 執行流程（complete 前的回報 SOP）

### 現有機制盤點

| 機制 | 覆蓋場景 | 缺口 |
|------|---------|------|
| Solution 「Spawn 落地確認」 | ANA ticket 的分析結論 spawn | 僅 ANA；自由格式；agent 自己建表格 |
| spawned\_tickets frontmatter | PM 建 ticket 後的追蹤 | 只記已建立的 ticket，不記「建議建立」 |
| NeedsContext section | agent 回報資料缺口 | 語意不同——缺料 vs 建議開票 |
| Exit Status section | agent 結束狀態 | 語意不同——完成狀態 vs 建議開票 |

## 重現實驗結果
### 實驗方法

盤點現有 CANONICAL\_BODY\_SECTIONS（9 章），確認無任何章節語意覆蓋「建議開票」。

### 實驗執行

現有 9 章節語意：

| 章節 | 語意 | 覆蓋「建議開票」？ |
|------|------|------------------|
| Task Summary | 任務摘要 | 否 |
| Problem Analysis | 問題分析 | 否（分析本 ticket 問題，非回報新問題） |
| 重現實驗結果 | 實驗記錄 | 否 |
| Solution | 解決方案 | 部分（ANA spawn 規劃在此，但語意是「結論的一部分」非獨立回報） |
| Test Results | 測試結果 | 否 |
| Context Bundle | 派發前 context | 否（PM 寫入，非 agent） |
| NeedsContext | 資料缺口 | 否（缺料 ≠ 建議開票） |
| Exit Status | 結束狀態 | 否（完成狀態 ≠ 建議開票） |
| Completion Info | 完成資訊 | 否 |

### 實驗發現

**已驗證事實**：
1. 現有 9 章節無任何一個的語意是「agent 建議 PM 開新 ticket」
2. ANA 的 Solution 內 Spawn 落地確認是「慣例」非「專屬章節」，且僅適用 ANA
3. NeedsContext 語意最接近但不同——缺料是「我需要什麼才能繼續」，建議開票是「我發現了什麼應該追蹤」
4. 現有 frontmatter spawned\_tickets 記錄的是「已建立的 ticket」，不是「建議建立的 ticket」——兩者是 request vs fulfillment 關係
