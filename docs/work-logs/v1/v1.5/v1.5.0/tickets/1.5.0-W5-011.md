框架現有三個錯誤/知識載體，跨專案能力不同：

| 載體 | 位置 | 跨專案傳播機制 | 現況缺口 |

| framework-issue | 框架 canonical repo（gh CLI） | canonical 追蹤、跨 consumer 修復 | 追蹤導向，非知識累積本體 |

### 已知升級流程與斷點

- `continuous-learning` skill 有「四問升級評估」（memory → 是否升級為 framework rule/methodology/error-pattern）——**機制存在**。

- 斷點：本地 memory 捕獲後，沒有系統性的「跨專案價值偵測 → 升級 → 去重 → 衝突處理」流程；依賴人工每案判斷。

### WRAP 分析摘要

**W（擴增選項）**——候選方案涵蓋三類性質（新增工具 / 改造既有 / 零工具），並經反向思考重定義問題：

| 方案 | 性質 | 內容 |
|------|------|------|
| A 流程強化 | 改造既有 | 四問評估結果結構化記錄（memory frontmatter `upgrade:` 欄位），reminder hook 升級為可驗證提示 |
| B 工具化升級 | 新增工具 | `promote` 命令一步完成「建 error-pattern 檔（allocator 編號）+ memory 加註 + MEMORY.md 修剪」，直接消除規則 7 指出的「升級摩擦」 |
| C 捕獲時分流 | 改造既有（規則層，零程式碼） | 錯誤學習類知識**預設直接寫 error-pattern**（canonical 層），memory 只留專案特定 context 與 pointer；把四問從「寫入後補救」前移為「寫入時分流」 |
| D 節奏稽核 | 零工具 | version-release check 掛「memory 升級稽核」：發版前掃描未標註升級狀態的 feedback memory，積壓可見化 |

**反向思考（問題重定義）**：用戶原始框架是「memory 無法跨專案」，反面問題是「錯誤學習為何會落在 memory」。並非所有 memory 都該跨專案（project_ 類本來就該本地）；真正斷點是**分流判斷發生在錯的時間點（事後）且無記錄**。此重定義使方案 C 成為核心，A/B/D 為配套。

**R（現實檢驗）**：

- 基本率：「提醒層 + 事後 checklist」型合規在本框架歷史成功率低——PC-061 本身即此類失敗記錄；W9-003 統計 38% 未升級；本實驗 4% 標註率。再加一層提醒不會改變結果。
- 依 opinionated-default-design 規則：「寫文件提醒使用者遵守」即工具預設行為待改善的信號；AI agent 場景（無跨 session 記憶）此信號加倍。方案 B/C 正是把提醒轉為預設路徑。
- Ooch 試水溫：C 的最小版本為修訂 upgrade-decision-tree + 規則 7 的預設目的地，零程式碼、單一 DOC ticket 可先行，失敗回退成本為 git revert。
- Steelman 被放棄選項：純 D 不增加工具面積、利用既有發版節奏；缺點是批次清帳認知負擔大、稽核只暴露積壓不降低摩擦，無法阻止增量。

**A（拉開距離）**：機會成本上，130 檔中約 42% 無 canonical 對應的知識正持續性跨專案流失，每個新專案重複踩雷；相對地全套落地約 3 個 ticket 容量。10 個月尺度：新 consumer 專案 clone 框架即獲得完整錯誤學習積累。悖論檢查：本設計寫入 `.claude/`（隨 sync 傳播），不自我違反；分流為預設非強制，保留用戶覆蓋。

**P（premortem 三原因 + 早期警訊）**：

| 失敗原因 | 早期警訊（可觀測） | 防護 |
|---------|------------------|------|
| 分流規則被忽略（重蹈 reminder 覆轍） | 發版稽核（spawn 3）顯示新增 feedback memory 中錯誤學習類佔比未降 | promote 工具讓正確路徑成為最低摩擦路徑；稽核 ticket 產出作為 spawn 強制層 hook 的 trigger |
| error-pattern 低價值膨脹 | error-patterns README 統計增速異常、query 命中雜訊上升 | 保留決策樹情境 C「單一事件未成熟暫存 memory」緩衝，分流判準含成熟度門檻 |
| 跨專案撞號/衝突增多 | sync-push 撞號偵測觸發頻率上升 | 既有 allocator + lineage 重編號機制已覆蓋，監控即可，不新增機制 |

### 設計方案結論

採 **C（捕獲時分流）為核心 + B（promote 工具）降摩擦 + D（發版稽核）兜底**；A 的結構化記錄併入 B（promote/defer 動作即寫 frontmatter 標註，記錄成為工具副作用而非額外步驟）。

三段流程設計：

1. **捕獲時分流**（規則層）：寫入錯誤學習類知識時即問「跨專案適用？」——是 → 直接 `/error-pattern add`（allocator 編號 + sync 傳播），memory 僅留一行 pointer；否/未成熟 → feedback memory + frontmatter 標註 `upgrade: deferred` 與理由。CC 原生 memory 機制不變（Never break userspace），僅改變框架指引的預設目的地。
2. **升級工具化**（工具層）：`promote` 一步完成建檔 + 編號 + 原檔加註 + MEMORY.md 修剪；`scan` 列出未評估/deferred 積壓。
3. **節奏稽核**（稽核層）：version-release check 增列 memory 升級稽核項，積壓與分流遵循率可見化；稽核結果作為是否需要強制層 hook 的決策 trigger。

**去重/衝突處理**：沿用既有三機制——error-pattern 來源前綴（`<CATEGORY>-<PROJ>-NNN`）防併發撞號、sync 腳本撞號偵測 + lineage 認領、framework-issue canonical issue 作跨 consumer 去重 key。本分析確認其成熟，不新增機制。

### 取捨

| 取捨點 | 接受的代價 | 理由 |
|-------|-----------|------|
| 捕獲時分流增加寫入時判斷負擔 | 每次記錄多一個分流判斷 | 判斷本來就該做（四問第一問），只是時點前移；事後補救模式已被證明不執行 |
| error-pattern 增長加速 | 索引/README 體量壓力 | 成熟度門檻緩衝 + 知識進 canonical 本就是設計目標；體量問題由警訊 2 監控 |
| sync-push 仍人工觸發，傳播非即時 | 跨專案延遲以 push 節奏為上限 | push 節奏屬既有 sync 工作流，本分析不擴大範圍；稽核層可見化積壓已足夠 |
| 不立即建強制層 hook | 分流初期依賴規則自律 | 強制層價值依賴「分流規則失效」證據；trigger 綁定 spawn 3 稽核 ticket 產出，非無 trigger 延後 |
