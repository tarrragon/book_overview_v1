| 方案 | 性質 | 內容 |
|------|------|------|
| A 流程強化 | 改造既有 | 四問評估結果結構化記錄（memory frontmatter `upgrade:` 欄位），reminder hook 升級為可驗證提示 |
| B 工具化升級 | 新增工具 | `promote` 命令一步完成「建 error-pattern 檔（allocator 編號）+ memory 加註 + MEMORY.md 修剪」，直接消除規則 7 指出的「升級摩擦」 |
| C 捕獲時分流 | 改造既有（規則層，零程式碼） | 錯誤學習類知識**預設直接寫 error-pattern**（canonical 層），memory 只留專案特定 context 與 pointer；把四問從「寫入後補救」前移為「寫入時分流」 |
| D 節奏稽核 | 零工具 | version-release check 掛「memory 升級稽核」：發版前掃描未標註升級狀態的 feedback memory，積壓可見化 |

**反向思考（問題重定義）**：用戶原始框架是「memory 無法跨專案」，反面問題是「錯誤學習為何會落在 memory」。並非所有 memory 都該跨專案（project_ 類本來就該本地）；真正斷點是**分流判斷發生在錯的時間點（事後）且無記錄**。此重定義使方案 C 成為核心，A/B/D 為配套。

**已評估未採納的選項**（多視角審查補列，區分「未想到」與「評估後放棄」）：

| 選項 | 未採納理由 |
|------|-----------|
| CC user-level `~/.claude/CLAUDE.md` + @import（機器層跨專案載體，CC 原生、即時生效） | 機器本地不隨 repo 傳播（協作者/新機器拿不到）、無 git 稽核、無編號/去重機制，不能作 canonical。knowledge-carrier-allocation 地圖對 user-level 層無條目屬系統性盲區，併入 spawn #2 補條目 |

| framework-issue `create --label candidate` 作未成熟知識 inbox（摩擦近 memory 寫入、跨 consumer 即時可見） | 依賴 gh/網路、不進 `/error-pattern query` 本地查詢路徑、candidate 可能形成第二積壓場。不作預設，於 spawn #1 決策樹修訂中列為「未成熟但明顯跨專案」的可選第三去向，deferred 積壓由稽核一併掃描 |

**R（現實檢驗）**：

- 基本率：「提醒層 + 事後 checklist」型合規在本框架歷史成功率低——PC-061 本身即此類失敗記錄；W9-003 統計 38% 未升級；本實驗 4% 標註率。再加一層提醒不會改變結果。
- 依 opinionated-default-design 規則：「寫文件提醒使用者遵守」即工具預設行為待改善的信號；AI agent 場景（無跨 session 記憶）此信號加倍。方案 B/C 正是把提醒轉為預設路徑。
- Ooch 試水溫：C 的最小版本為修訂 upgrade-decision-tree + 規則 7 的預設目的地，零程式碼、單一 DOC ticket 可先行，失敗回退成本為 git revert。
- Steelman 被放棄選項：純 D 不增加工具面積、利用既有發版節奏；缺點是批次清帳認知負擔大、稽核只暴露積壓不降低摩擦，無法阻止增量。

**A（拉開距離）**：機會成本上，130 檔中約 42%（55 檔）無 canonical 對應——此為跨專案流失量的**上限估計**（未逐檔區分合法專案本地 memory 與被困的通用知識，逐檔判定歸 backlog 清理執行時處理）；即使大幅折減，流失仍屬持續性損失且隨規模增長；相對地全套落地約 3 個 ticket 容量。10 個月尺度：新 consumer 專案 clone 框架即獲得完整錯誤學習積累。悖論檢查：本設計寫入 `.claude/`（隨 sync 傳播），不自我違反；分流為預設非強制，保留用戶覆蓋。

**P（premortem 三原因 + 早期警訊）**：

| 失敗原因 | 早期警訊（可觀測） | 防護 |
|---------|------------------|------|
| 分流規則被忽略（重蹈 reminder 覆轍） | 發版稽核（spawn 3）顯示新增 feedback memory 中錯誤學習類佔比未降 | promote 工具讓正確路徑成為最低摩擦路徑；稽核 ticket 產出作為 spawn 強制層 hook 的 trigger |
| error-pattern 低價值膨脹 | error-patterns README 統計增速異常、query 命中雜訊上升 | 保留決策樹情境 C「單一事件未成熟暫存 memory」緩衝，分流判準含成熟度門檻 |
| 跨專案撞號/衝突增多 | sync-push 撞號偵測觸發頻率上升 | 既有 allocator + lineage 重編號機制已覆蓋，監控即可，不新增機制 |
| 錯誤根因寫入 canonical 後跨專案傳播（表層根因經 sync 擴散，回收成本高於困在本地——已 pull 的 consumer 不會自動撤回） | error-pattern 修訂/推翻/supersede 頻率上升 | 分流判準以 Two-Phase Reflection 完成度為直寫 canonical 的前置門檻；根因未熟一律走 deferred（根因型知識「先 memory 後升級」是預設經過，非例外） |

### 設計方案結論

採 **C（捕獲時分流）為核心 + B（promote 工具）降摩擦 + D（發版稽核）兜底**；A 的結構化記錄併入 B（promote/defer 動作即寫 frontmatter 標註，記錄成為工具副作用而非額外步驟）。

三段流程設計：

1. **捕獲時分流**（規則層）：寫入錯誤學習類知識時即問「跨專案適用**且根因已過 Two-Phase Reflection**？」——兩者皆是 → 直接 `/error-pattern add`（allocator 編號 + sync 傳播），memory 僅留一行 pointer；否/根因未熟 → feedback memory + frontmatter 標註 `upgrade: deferred` 與理由。CC 原生 memory 機制不變（Never break userspace），僅改變框架指引的預設目的地。本設計消除的不是分流判斷（判斷屬特例顯式化而非消除），而是**不可觀測的中間態**——舊流程「已寫入未評估」態不可查證、無限積壓（130 檔即此態的累積）；前移後每筆寫入時態即確定（canonical / deferred+理由），deferred 為顯式標註態，仍由稽核收割。
2. **升級工具化**（工具層）：`promote` 一步完成建檔 + 編號 + 原檔加註 + MEMORY.md 修剪；`scan` 列出未評估/deferred 積壓。
3. **節奏稽核**（稽核層）：version-release check 增列 memory 升級稽核項，積壓與分流遵循率可見化；稽核結果作為是否需要強制層 hook 的決策 trigger。

**去重/衝突處理**：沿用既有三機制——error-pattern 來源前綴（`<CATEGORY>-<PROJ>-NNN`）防併發撞號、sync 腳本撞號偵測 + lineage 認領、framework-issue canonical issue 作跨 consumer 去重 key。機制存在且撞號防護經實查成熟，但兩項既知限制須隨行監控，不可宣稱全面成熟：(1) grep 級去重有同根異名死角（1.5.0-W3-001 已記錄、framework issue #14 追蹤 cbm 語意去重路徑）——捕獲時分流會放大寫入量與碰撞面積，稽核項須含近似重複掃描；(2) lineage 重編號會使 memory 內 pointer 變 dangling——promote 工具的 scan 須含 dangling pointer 檢查。

### 取捨

| 取捨點 | 接受的代價 | 理由 |
|-------|-----------|------|
| 捕獲時分流增加寫入時負擔 | 分流判斷 + 「是」分支的完整建檔成本（`/error-pattern add` 為多步流程，重於 memory 單檔寫入） | 判斷本來就該做（四問第一問），只是時點前移且事後補救模式已被證明不執行；建檔摩擦由 promote 工具吸收，故工具票與規則票**並行落地**，不留「規則先行無工具」的高摩擦窗口 |
| error-pattern 增長加速 | 索引/README 體量壓力 | 成熟度門檻緩衝 + 知識進 canonical 本就是設計目標；體量問題由警訊 2 監控 |
| sync-push 仍人工觸發，傳播非即時 | 跨專案延遲以 push 節奏為上限 | push 節奏屬既有 sync 工作流，本分析不擴大範圍；稽核層可見化積壓已足夠 |
