## Problem Analysis

### 現況盤點（PM 前台，供分析起點；本 session 實地走過 memory→PC-092 為第一手素材）

框架現有三個錯誤/知識載體，跨專案能力不同：

| 載體 | 位置 | 跨專案傳播機制 | 現況缺口 |
|------|------|--------------|---------|
| memory | `~/.claude/projects/<proj>/memory/` | 無——專案本地，不隨 `.claude` sync | CC 默認捕獲路徑，天生 local；用戶指出的核心落差 |
| error-patterns | `.claude/error-patterns/PC\|IMP\|ARCH` | 隨 `.claude` sync-push/sync-pull 跨專案傳播 | 已跨專案，但「從 memory 升級進來」是人工逐案判斷 |
| framework-issue | 框架 canonical repo（gh CLI） | canonical 追蹤、跨 consumer 修復 | 追蹤導向，非知識累積本體 |

### 已知升級流程與斷點

- `continuous-learning` skill 有「四問升級評估」（memory → 是否升級為 framework rule/methodology/error-pattern）——**機制存在**。
- 但升級**觸發是 ad-hoc**：本 session PC-092 v3 是「用戶提示」才升級，非系統化偵測「這個 memory 該升級」。
- 斷點：本地 memory 捕獲後，沒有系統性的「跨專案價值偵測 → 升級 → 去重 → 衝突處理」流程；依賴人工每案判斷。

### 分析需回答的核心問題（供 claim 後展開）

1. memory（local 捕獲便利）與 error-pattern（cross-project canonical）的分工是否合理？還是 memory 該有「可跨專案」的子類？
2. 「本地 → canonical」升級該由什麼系統化訊號觸發（而非人工）？
3. 跨專案傳播時的去重、版本衝突、專案特異性 vs 通用性判定如何處理？
4. 與 CC 默認 memory 機制的相容性（不能破壞 CC 原生行為，Never break userspace）。

`.claude/skills/continuous-learning/`、`.claude/skills/error-pattern/`、`.claude/skills/framework-issue/`、`.claude/scripts/sync-claude-{push,pull}.py`、既有 memory feedback 索引 MEMORY.md。
