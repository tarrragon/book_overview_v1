# Execution Log

## Task Summary

評估 multi_view_status hook 警告訊息改善（顯示正確格式範例）

## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

hook WARNING 訊息列出合法值和子欄位要求，但未展示正確寫入格式範例。LLM 看到「skipped 需附 reason」後直覺寫成 heading 結構：

```markdown
### multi_view_status    ← LLM 自然傾向
status: skipped
reason: ...
```

而 hook \_parse\_field 用 regex \`^\\s\*multi\_view\_status\\s\*:\\s\*(.+?)\\s\*\$\` 搜尋，期望 flat key-value：

```markdown
multi_view_status: skipped
reason: ...
```

### 影響範圍

- \`.claude/hooks/acceptance\_checkers/multi\_view\_checker.py\` 的 \_format\_missing\_warning 函式

### 相關 Error Pattern

- opinionated-default-design 原則：「預設行為 > 文件規範」——WARNING 訊息是 LLM 的即時引導，應展示格式範例

## 重現實驗結果
### 實驗方法

1. 檢視 \_format\_missing\_warning 輸出的完整文字
2. 與 W5-015 實際寫入的格式比對

### 實驗執行

hook 輸出的 WARNING 訊息：
- 列出合法值：reviewed, skipped, n\_a
- 列出子欄位要求：skipped 需附 reason
- **未包含正確寫入格式的具體範例**

W5-015 實際寫入（被 hook 判定為缺失）：
- 使用 heading 格式 \`### multi\_view\_status\` + 下方 \`status: skipped\`
- hook regex 搜尋 \`multi\_view\_status: <value>\` 行未匹配

### 實驗發現

**已驗證事實**：
1. hook 的 WARNING 訊息確實未顯示寫入格式範例（confirmed by source code inspection）
2. LLM 寫錯格式（heading vs flat）是 W5-015 的實際發生案例
3. hook \_format\_invalid\_value\_warning 有 nested YAML 偵測（PC-117 / W17-111），但 \_format\_missing\_warning 無格式引導
4. 問題本質是 opinionated-default 信號：「提醒遵守格式」→ 應改為「工具展示正確格式」

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 方案比較

**方案 A：WARNING 訊息加格式範例（推薦）**

在 \_format\_missing\_warning 末尾加一段正確格式範例：

\`\`\`
正確寫法（在 Solution 區段內）：
  multi\_view\_status: skipped
  reason: <跳過理由>
\`\`\`

| 維度 | 評估 |
|------|------|
| 成本 | 極低（改 1 個函式的字串輸出，約 5 行） |
| 效果 | 高——LLM 看到格式範例後直接 copy 結構，不需推斷 |
| 風險 | 無——純訊息文字變更，不影響邏輯 |
| 對齊 | opinionated-default 原則主張 1（預設行為 > 文件規範）+ 主張 3（AI agent 加倍） |

**方案 B：hook 兼容 heading 格式**

修改 \_parse\_field 兼容 \`### multi\_view\_status\` heading 下方的 \`status: <value>\` 格式。

| 維度 | 評估 |
|------|------|
| 成本 | 中（改 regex + 補測試 + 語意歧義處理） |
| 效果 | 中——解決寫錯格式不報 WARNING，但引入語意歧義（heading 下可能有其他 key） |
| 風險 | 中——regex 複雜化，且 heading 內多 key 時 parse 行為不確定 |
| 對齊 | 不對齊——問題源頭是 LLM 不知道正確格式，兼容錯誤格式是繞過而非解決 |

**方案 C：維持現狀**

| 維度 | 評估 |
|------|------|
| 成本 | 零 |
| 效果 | 零——同樣的錯誤會反覆發生 |

### 結論

**採方案 A（WARNING 訊息加格式範例）。** 理由：

1. 成本極低（5 行字串修改），效果高（LLM 直接 copy）
2. 符合 opinionated-default 主張 1+3——工具即時引導是 AI agent 唯一可靠防線
3. 方案 B 治標不治本——兼容錯誤格式掩蓋根因，且引入語意歧義
4. \_format\_invalid\_value\_warning 已有 nested YAML 偵測（PC-117），可參考其模式在 missing 訊息也加格式引導
