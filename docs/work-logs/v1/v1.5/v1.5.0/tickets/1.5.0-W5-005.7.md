## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 實作內容

`track_stale_list.py` 擴充（staleness.py 原語零改動，長在既有輪子上）：

- `_collect_stale_in_progress()`：status == in_progress 且 `is_stale_in_progress()`（frontmatter started_at，>= 24h）的票，附 `_minutes` 依經過時間降序；`--wave` 過濾同步作用。
- `_render_in_progress_section()`：table 輸出於 pending 表格後追加章節，逐列顯示 `id | in_progress Nh | agent=<who.current> | title`，章節尾附一行 release 提示（`ticket track release <id>`，明示進行中 agent 勿用）。
- `execute_stale_list()` 僅 table 格式渲染新章節；新增 `_now` 測試注入 hook（與既有 `_today` 對稱）。

### Acceptance 2：單平面設計論證

判定完全依 frontmatter `started_at`（`is_stale_in_progress` 既有原語，與 runqueue [STALE] tag / dashboard 同源），**不讀 dispatch-active.json**——母票 D7 審查已指出引入 dispatch-active 交叉比對會自造第三平面雙面帳（自違 F6）；ticket 世界平面已足以回答「滯留多久」，無必要性論證成立空間，故零依賴。

### Acceptance 3：與 subagent-stop-dispatch-cleanup-hook 職責去重

| 維度 | subagent-stop-dispatch-cleanup-hook | 本擴充 |
|------|-------------------------------------|--------|
| 觸發 | SubagentStop 事件（agent 真正停止） | 查詢時（PM 執行 stale-list） |
| 資料平面 | dispatch-active.json（派發記錄） | ticket frontmatter started_at（世界平面） |
| 動作 | 清理記錄 + [OK]/[WAIT] 廣播 | 呈現滯留清單 + release 指令提示 |
| 覆蓋缺口 | agent 已不在（無 SubagentStop 事件）的遺留 in_progress 無法觸發 | 正是捕捉此缺口（事件遺失後的查詢面補位） |

兩者無重疊：hook 管事件面記錄清理，本命令管查詢面狀態呈現；皆不自動 release（人工確認 agent 已終止後執行，防誤釋放進行中任務）。
