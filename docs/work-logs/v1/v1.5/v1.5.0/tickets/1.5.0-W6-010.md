## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

roster 的 {language}-developer 執行代理人模式僅覆蓋 Dart/Flutter（parsley）、Go（fennel）、Python（thyme-python），專案主語言 JavaScript 無對應 Phase 3b 執行代理人。thyme-extension-engineer 定義檔明示「本代理人負責技術規劃而非實際編碼。所有程式碼實作由執行代理人執行」（定義檔 L48），但 CLAUDE.md §4 曾 stale 指定其為實作代理人，於 W6-001 執行期間引發角色衝突；W6-009 已將文件修正為「實作 general-purpose（過渡）」，本票評估過渡安排是否轉為永久或建專屬定義。

### 影響範圍

- 派發面：所有 src/ 下 JS 實作派發。里程碑 v1.5.0–v1.11.0 全為多書城適配器開發（8 個版本的 JS 實作工作量），general-purpose 無語言知識庫、無三區塊職責邊界、無 quality reference 強制載入。
- 資產面：`.claude/agents/`（缺 JS developer 定義）、`.claude/references/`（缺 quality-javascript.md；現有 quality-dart / quality-go / quality-python + quality-language-template）。

### 相關 Error Pattern

無直接對應 PC。相關規範：`.claude/rules/core/agent-definition-standard.md`（三區塊標準）、W5-001 派發越界事件（agent 職責邊界模糊的動機案例）。

## 重現實驗結果
### 實驗方法

以固定值命令盤點 roster 實際狀態，驗證 ticket 宣稱的三項事實：(1) roster 無 JS 執行代理人；(2) thyme-extension-engineer 為純規劃；(3) 建新代理人的模板資產存在性。

### 實驗執行

1. `ls .claude/agents/` → 34 檔；grep "Phase 3b" 命中的實作類定義僅 parsley-flutter-developer / fennel-go-developer / thyme-python-developer / language-agent-template（模板本身）。
2. `grep 不實作 thyme-extension-engineer.md` → L48「本代理人負責技術規劃而非實際編碼。所有程式碼實作由執行代理人執行」。
3. `ls .claude/references/ | grep quality` → quality-dart.md / quality-go.md / quality-python.md / quality-language-template.md 存在，**quality-javascript.md 不存在**。
4. `grep 3b registry.yaml` → phase3b 註冊僅 parsley / thyme-python / fennel-go 三者。
5. 讀 W6-009 ticket → 確認衝突鏈：CLAUDE.md §4 stale 指定 thyme 為實作代理人 → W6-009 改為 general-purpose（過渡）→ 本票評估永久解。

### 實驗發現

**已驗證事實**：roster JS 執行代理人缺口為真；thyme 純規劃定位明文；language-agent-template.md 與 quality-language-template.md 兩模板齊備，新建成本低；registry.yaml phase3b 無 JS 條目。

**仍未驗證假設**：general-purpose 執行 JS 實作的「實際品質劣化程度」無統計資料——W6-001 是角色衝突事件（派發指定錯誤），非 general-purpose 產出品質不良的直接證據。本票結論不依賴此假設，改以「知識庫缺失 + 職責邊界缺失」的結構性風險與 8 版本工作量為依據。

### 盤點表：roster 執行代理人語言覆蓋（acceptance 1）

覆蓋倒掛：使用度最高的語言是唯一無專屬執行代理人者。

### WRAP 評估（acceptance 2）

**W 候選方案**（涵蓋新增 / 改造既有 / 零工具三類）：
- A 新增：依 language-agent-template 建 JS 專屬實作代理人 + quality-javascript.md + registry.yaml 註冊
- B 改造既有：擴充 thyme-extension-engineer 為規劃+實作雙職——否決，違反 roster 規劃/實作分離核心模式（Phase 3a/3b 分離），且正是 W6-001 衝突的錯誤方向
- C 零工具：長期沿用 general-purpose，JS 規範靠每次派發 prompt 引用——品質不穩且違反 PC-040 精神（context 該在穩定載體不在 prompt）
- D 半措施：只建 quality-javascript.md 供 general-purpose 引用，不建代理人——補知識庫但仍缺三區塊職責邊界與 registry 派發錨點；為 A 的真子集

**R 現實檢驗**：{language}-developer 模式已被 3 個既有代理人驗證（基本率高）；兩模板齊備使 A 的建置成本低。Steelman C：general-purpose 工具全開、model 跟隨主線程（可能強於模板預設 haiku）、零維護成本——此優點以 IMP 設計時 model 欄位顯性評估來吸收，不構成放棄 A 的理由。

**A 機會成本**：A 為一次性投入，回報跨 v1.5–v1.11 八個版本的每次 JS 派發；C 的成本是每次派發重複貼規範 + 品質波動。10 個月後仍在寫 JS 適配器，A 的回報持續。本票 when 已定「W6 完成後或下版本規劃波」執行，不擠壓 W6 收尾。

**P 行前預想**（失敗原因 → 早期警訊 → 防護，寫入 spawn IMP acceptance）：
1. quality-javascript.md 內容單薄，agent 行為與 general-purpose 無差異 → 警訊：首兩次派發產出 review 與規範無關聯 → 防護：acceptance 要求覆蓋 Chrome Extension 關鍵限制（自 chrome-extension-quickref 抽取）與 ES Module / Jest 專案慣例
2. 模板預設 model: haiku 不適配複雜 Extension 實作 → 警訊：首次派發回合耗盡或測試通過率低 → 防護：IMP 內顯性評估 model 欄位
3. registry.yaml / hook 未同步致 dispatch 不認得新 agent → 警訊：agent-definition-standard-check-hook 或 dispatch hook 告警 → 防護：acceptance 含 registry 註冊 + session-start 掃描通過

**評估結論**：採方案 A。品質維度——語言知識庫 + 三區塊職責邊界 + quality reference 強制載入，消除 W6-001 類角色衝突的結構根因；維護成本維度——一次性建置（兩模板齊備），後續維護與既有 3 個 developer 同模式，邊際成本低。
