## 重現實驗結果
### 根因假設與驗證（WRAP R 階段）

**接受中的根因假設**：「token 值雙端硬編碼 + 人工 diff 同步，會持續產生漂移失效」。

**實驗 1：同步失效實證（已驗證的事實）**
- V1 primary 於 0.19.1-W3-001（commit a991bce65）改為 #1A56DB（WCAG AA 校色），APP 端 spec §14.6 差異標記僅記載 rsp vs px 單位差異，**色值分歧未入契約**——人工同步已實際失效 1 次。
- V1 缺 divider 系列 token（APP 已有 dividerSubtle/Normal/Strong），覆蓋面漂移靠 2026-07-11 人工盤點才發現。

**實驗 2：token 變更頻率量測（git log 實測）**
- V1 `src/core/design-system/*.js`（4 檔，不含生成物）：歷史共 9 commits，其中**值變更僅 1 次**（a991bce65 Wave B 配色），餘為建立/CJS 化/lint/語意重命名等結構調整。
- APP 端（含 0.37.0 搬遷前舊路徑 ui_config/flat_design_config）：共 10+1 commits，型態同樣以結構調整為主。

**已驗證 vs 未驗證**
- 已驗證：同步失效發生過（1 次）；「值變更」頻率極低（年約 1 次）；「覆蓋面擴張」是進行式（PROP-016 divider/石碑刻痕系列、PROP-013 將反向補 V1）。
- 未驗證：APP 端 Dart 生成機制可行性（build_runner vs pre-build script）；Style Dictionary 對 Flutter/Dart 輸出的支援成熟度。

**對根因假設的修正**：漂移主要來源是「新 token 增補時的覆蓋面不同步」而非「既有值頻繁變更」。全自動生成 pipeline 的 ROI 需以低值變更頻率折算；「機器可讀對照 + 自動校驗」的偵測價值則由失效實證直接支撐。此修正使候選空間新增輕量校驗層方案（見 Solution 候選 D）。

## Solution

### 多視角審查記錄（heavy 級：linux + thyme-extension-engineer，2026-07-11）

**兩視角排序一致：D > B >> A ≈ E**（C 基線已被用戶否決不評）。

**linux（品質/架構視角）**：
- D 採用——唯一與實測資料對齊：漂移是偵測問題就用偵測層解決；把「平台校準是合法分歧」當一等公民（對照表自然一列）而非 base+override 的特例補丁；零破壞現有 pipeline。
- A 否決（148 行 token + 年 1 次值變更，引入需自訂 Dart format 的外部工具，複雜度超過問題一個數量級）；B 否決（為年 1 次變更維護兩個生成器 + schema 治理）；E 否決（與平台校準仲裁正面衝突 + Dart 解析脆弱，方向性錯誤）。
- 關鍵發現 1：實查 colors.js，V1 **整個 palette** 是 0.19.1-W3-001 有意校準（非僅 primary），base+overrides 結構下覆蓋會常態化——若校準比例 > 30%，A/B 前提崩塌。全量 token 分歧盤點列為 D 實作的第一個工作項。
- 關鍵發現 2：token 檔行內註解（WCAG 對比數據、決策 ticket 引用）是活文件資產，生成物化會流失。
- 關鍵發現 3（D 成立的必要條件）：校驗必須**雙向**——manifest 所列 token 檢查雙端存在且值符，且雙端存在的 token 檢查 manifest 有記載（新增 token 未入 manifest 即紅燈），否則只是把「spec 漏記」搬家成「manifest 漏記」。
- 過度工程訊號：以多書城擴張為生成方案辯護混淆了「消費者成長」與「變更頻率成長」——多書城增加 token 消費者，不增加值變更頻率。

**thyme-extension-engineer（Extension 技術可行性視角）**：
- D 對 esbuild bundle / CJS 消費介面（9 個 require 消費檔）/ snapshot test / MV3 CSP **零改動**。
- 既有缺口發現：`npm run validate:design-system` 是孤兒腳本——註解聲稱 CI 把關，實際未接入 lint.yml / lint-staged / 任何 test script，只能人工執行。D 落地時一併接線，成本邊際。
- D 自然落點：新增 npm script（比照 validate:design-system 模式）+ 接入 `.github/workflows/lint.yml` step；**不是 .claude/hooks**（session-scoped 攔截防不了非 Claude Code 來源的變更，違反專案雙層防線設計）。
- 跨 repo 校驗次階段化：先落地「V1 manifest vs V1 值」單端校驗（repo 內自足），跨 repo 比對（需 CI checkout 兩 repo）作次階段，不阻塞最小可行版本。
- A 補充成本：Style Dictionary 屬 devDependency 不進 CE runtime（無 MV3/上架影響），但有 npm audit 表面擴大 + 需比照 ensureEsbuildAvailable() 補 fail-fast 前置驗證（W1-080 模式）兩項隱含債務。

### 整合結論（PM）

採用 D（token manifest 校驗層）為第一階段方案：機器可讀 manifest（token 名對照 + base 值 + 平台覆蓋 + 理由）+ 雙向校驗（npm script + CI step）。「值層統一」語意修正為「分歧受控可見」（Consider the Opposite 結論 + 用戶色值仲裁的自然延伸）。升級路徑：manifest schema 可演化為 B/A 的 SSOT 輸入，升級 trigger 綁定實測數據（token 值變更頻率顯著上升時建評估 ticket），不封死。待用戶確認。
