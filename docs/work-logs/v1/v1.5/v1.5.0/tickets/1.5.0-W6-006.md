## 重現實驗結果
### 根因假設與驗證（WRAP R 階段）

**接受中的根因假設**：「token 值雙端硬編碼 + 人工 diff 同步，會持續產生漂移失效」。

**實驗 1：同步失效實證（已驗證的事實）**
- V1 primary 於 0.19.1-W3-001（commit a991bce65）改為 #1A56DB（WCAG AA 校色），APP 端 spec §14.6 差異標記僅記載 rsp vs px 單位差異，**色值分歧未入契約**——人工同步已實際失效 1 次。
- V1 缺 divider 系列 token（APP 已有 dividerSubtle/Normal/Strong），覆蓋面漂移靠 2026-07-11 人工盤點才發現。

**實驗 2：token 變更頻率量測（git log 實測）**
- V1 `src/core/design-system/*.js`（4 檔，不含生成物）：歷史共 9 commits，其中**值變更僅 1 次**（a991bce65 Wave B 配色），餘為建立/CJS 化/lint/語意重命名等結構調整。
- APP 端（含 0.37.0 搬遷前舊路徑 ui_config/flat_design_config）：共 10+1 commits，型態同樣以結構調整為主。

**已驗證 vs 未驗證**
- 已驗證：同步失效發生過（1 次）；「值變更」頻率極低（年約 1 次）；「覆蓋面擴張」是進行式（PROP-016 divider/石碑刻痕系列、PROP-013 將反向補 V1）。
- 未驗證：APP 端 Dart 生成機制可行性（build_runner vs pre-build script）；Style Dictionary 對 Flutter/Dart 輸出的支援成熟度。

**對根因假設的修正**：漂移主要來源是「新 token 增補時的覆蓋面不同步」而非「既有值頻繁變更」。全自動生成 pipeline 的 ROI 需以低值變更頻率折算；「機器可讀對照 + 自動校驗」的偵測價值則由失效實證直接支撐。此修正使候選空間新增輕量校驗層方案（見 Solution 候選 D）。
