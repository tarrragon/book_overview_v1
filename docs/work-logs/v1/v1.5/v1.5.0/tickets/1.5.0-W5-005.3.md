## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 三方案成本效益比較

### 方案 A：現狀共享樹（執行緒模型）+ 精確 git add SOP

| 維度 | 評估 |
|------|------|
| 隔離程度 | 無。agent 與 PM 共用 index + working tree |
| 設定成本 | 零 |
| 已知事故 | PC-092（commit race）、PM Edit 越界 commit、PM 被迫讀不寫 |
| 緩解措施 | prompt 明示精確 git add 路徑（PC-092 SOP）、PM agent 跑時不 Edit |
| 適用場景 | 單一 agent 序列派發、.claude/ 純文件修改（PM 直做更划算） |
| 根本限制 | 並行 2+ agent 時無法保證 commit 邊界正確；PM 被鎖定純讀 |

### 方案 B：feat branch 派發

| 維度 | 評估 |
|------|------|
| 隔離程度 | 中。獨立 branch 但共用 working tree（需 checkout 切換） |
| 設定成本 | PM 派發前 `git checkout -b feat/<id>`；agent 完成後 PM `git checkout main && git merge feat/<id>` |
| 已知事故 | agent 自動 merge 回 main 繞過 PM 驗證（5 次派發中 3 次，memory feedback_dispatched_agent_branch_auto_merge）|
| 緩解措施 | prompt 三句齊備（commit 於 feat / 不要 merge / PM 驗證後合併） |
| 適用場景 | 單一 agent + PM 需同時前台工作；tests/ 修改（hook 不豁免 main） |
| 根本限制 | 不支援真正並行（同一時刻只有一個 branch checked out）；agent 自動 merge 行為不穩定 |

### 方案 C：worktree 隔離派發

| 維度 | 評估 |
|------|------|
| 隔離程度 | 高。獨立 working tree + 獨立 branch |
| 設定成本 | CC runtime 自動建立/清理 worktree；PM 需 push 或 worktree 基於 stale base |
| 已知事故 | stale base（IMP-066 / worktree 看不到未 push 的 commit）、.claude/ Edit transient deny（PC-115 三方 deadlock）、auto-stage merge conflict（ticket md 兩端同時編輯）、PM cwd 被自動切進 worktree |
| 緩解措施 | 派發前 git push、prompt 含絕對路徑提供檔案內容、merge conflict 用 --theirs |
| 適用場景 | 真正並行 2+ agent；agent 修改 src/ 或 tests/（非 .claude/） |
| 根本限制 | .claude/ 修改場景有三方 deadlock（hook 強制 worktree + PC-115 deny + commit gate）；worktree setup 有不可忽略的延遲與 stale 風險 |

### 事故分佈實證

從 memory feedback 統計事故密度：

| 隔離模式 | 事故數 | 事故類型 |
|---------|--------|---------|
| 共享樹 | 3 | PC-092 commit race、PM Edit 越界、PC-137 並行 deny |
| feat branch | 1 | 自動 merge 繞過驗證（3/5 次復現） |
| worktree | 5 | stale base、PC-115 deadlock、auto-stage conflict、cwd autoswitch、ticket CLI 不可見 |

表面看 worktree 事故最多，但這是因為 worktree 被用於最複雜的並行場景。校正使用頻率後，**三種模式的事故率相近**——問題不在哪個隔離模式，而在 PM 對該模式行為的預期是否準確。

### 結論：純 SOP 文件化，不做機制變更

**選擇：純 SOP 文件化（二擇一中選文件化）。**

理由：

1. **無單一最優模式**：三種模式各有明確適用場景，強制反轉預設會把一類事故換成另一類。CI runner 預設隔離 checkout 的類比不成立——CI 是無狀態一次性環境，本系統 agent 需讀 ticket md / .claude/ context，隔離越深讀取成本越高。

2. **事故已有對應防護**：PC-092（精確 git add SOP）、PC-115（PM fallback SOP）、worktree dispatch prerequisites（git push 前置）、auto-merge 防護（git ground truth 驗證）——每個事故點已有 memory feedback 或 error-pattern 覆蓋。

3. **機制變更成本不對稱**：反轉預設需修改 agent-dispatch-validation-hook、可能引入新的 hook 交互作用；而 SOP 文件化只需在 agent-dispatch-template.md 加一張決策表，零破壞風險。

4. **CC runtime 行為不確定性是真實約束**：agent 自動 merge、cwd autoswitch、transient deny 都是 CC runtime 行為而非本系統可控——機制層無法修正 runtime 的不確定性，但 SOP 可教 PM 用 git ground truth 驗證。

### SOP 文件化內容（建議寫入 agent-dispatch-template.md）

| 派發場景 | 建議隔離模式 | 理由 |
|---------|-------------|------|
| 單一 agent + 純 .claude/ 修改 | 共享樹（或 PM 直做） | worktree .claude/ 有 deadlock 風險 |
| 單一 agent + src/tests/ 修改 | feat branch | PM 可同時前台工作 |
| 並行 2+ agent + 檔案集互斥 | worktree | 唯一支援真正並行的模式 |
| 並行 2+ agent + 檔案集有交集 | 序列執行（禁並行） | 任何隔離模式都不解 merge conflict |

### Spawn 落地確認

無需建 ticket。結論為純 SOP 文件化，具體寫入動作可由 W5-005 母票收尾時統一處理或由 PM 直接執行（體量小於獨立 DOC ticket 閾值）。
