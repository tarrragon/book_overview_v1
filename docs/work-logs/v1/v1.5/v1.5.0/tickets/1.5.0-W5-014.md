## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

Confabulation 是 LLM 自回歸生成的數學行為（PC-166 L1-L3），不是工具呼叫行為。現有 6 層防護（A-F）全為規則層自律。W5-011.3 證實：即使規則存在，連驗證步驟的 stdout 也會被虛構（遞歸污染），規則層在高 tool-call 密度序列中失效。

核心矛盾：confabulation 是「模型不發工具呼叫而續寫預期結果」——恰好發生在 hook 系統盲區（hook 只能攔截實際的工具呼叫，不能攔截「模型沒有呼叫工具卻寫出看似工具結果的文字」）。

### 影響範圍

- `.claude/rules/core/tool-output-trust-rules.md`（規則 1-5，規則層自律）
- `.claude/error-patterns/process-compliance/PC-166-*.md`（防護 A-F）
- 所有涉及 mutation → 驗證的工作流（commit / complete / append-log / set-*）

### 相關 Error Pattern

- PC-166（confabulated tool result，6 層防護 A-F）
- PC-111（決策論述捏造技術機制）
- PC-147（reference doc confabulation cascade）

## 重現實驗結果
### 實驗方法

盤點 CC hook 事件類型與 confabulation 生成行為的交集，判斷 hook 能否攔截虛構文字生成。

### 實驗執行

**步驟 1：CC hook 事件類型盤點**

本專案已註冊的 hook 事件：
- PreToolUse: 11 hooks（工具呼叫前觸發）
- PostToolUse: 6 hooks（工具呼叫後觸發）
- SessionStart: 1 hook
- UserPromptSubmit: 1 hook
- SubagentStop: 1 hook
- Stop: 1 hook

CC 平台支援的全部事件（來源：claude-code-guide agent 知識）：
PreToolUse / PostToolUse / Stop / SubagentStop / SessionStart / SessionEnd / UserPromptSubmit / PreCompact / Notification

**步驟 2：Confabulation 生成行為分析**

Confabulation 的點火動作（PC-166 防護 F）：「工具呼叫發出後，在同一訊息續寫該工具的預期結果」。

此行為的本質是：模型在 tool_use 之後、下一個 tool_result 注入之前，繼續生成 text tokens。這是**模型生成行為**，不是工具呼叫行為。

**步驟 3：交集分析**

| Hook 事件 | 觸發時機 | 能否偵測 confabulation |
|-----------|---------|----------------------|
| PreToolUse | 工具呼叫前（有工具呼叫才觸發） | 否——confabulation 是「不呼叫工具卻寫結果」 |
| PostToolUse | 工具呼叫後（有工具呼叫才觸發） | 間接可能——可在 mutation 工具後注入驗證提示 |
| Stop | agent 結束時 | 事後審計——可驗證 claimed vs actual 狀態 |
| UserPromptSubmit | 用戶提交 prompt 時 | 否——不涉及模型生成行為 |
| PreCompact | context 壓縮前 | 否——不涉及工具結果 |

### 實驗發現

**已驗證事實**：
1. CC hook 系統無「AssistantTextGeneration」事件——hook 不能攔截模型的文字生成過程
2. confabulation 恰好發生在 hook 盲區（模型不發工具呼叫的時間窗口）
3. PostToolUse 是唯一可間接介入的事件（在真實工具呼叫後注入提示），但模型是否遵從提示仍屬自律層
4. Stop hook 可做事後審計（claimed mutations vs git ground truth），但無法預防

**仍未驗證的假設**：
- CC runtime 未來是否可能新增 AssistantMessage / TextGeneration 事件（需追蹤 CC release notes）
- PostToolUse 注入驗證提示的實際效果（是否比規則層更可靠——假設需實驗驗證）

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### WRAP 評估

### W（Widen）— 候選方案

| 方案 | 機制 | enforcement 層級 | 可行性 |
|------|------|-----------------|--------|
| A：PostToolUse 驗證提示注入 | mutation 工具（Bash:git commit / ticket CLI）PostToolUse hook 在 tool_result 附加「你必須在下一輪用固定值命令獨立驗證此操作結果」 | 介於規則與強制之間（注入 system 層提示，但模型仍可忽略） | 中——實作簡單，效果未驗證 |
| B：Stop hook 事後審計 | session 結束時比對 claimed mutations（從 transcript 提取 commit hash / complete 宣稱）vs git/ticket 真實狀態，報告差異 | 事後偵測（不預防） | 高——技術可行，但損害已發生 |
| C：CC runtime 層「mutation 後強制 readback」 | CC runtime 在 mutation 工具呼叫後，自動注入一個 read-only 工具呼叫驗證結果，才允許模型繼續生成 | 真正的強制層 | 不可行——需修改 CC runtime（非本專案可控） |
| D：Opinionated tool wrapper | 包裝 mutation CLI（ticket complete / git commit）為「執行 + 自動驗證 + 合併輸出」的複合工具，使模型收到的 tool_result 已含驗證結果 | 工具預設層（opinionated-default） | 中高——可在本專案 CLI 層實作 |
| E：維持規則層 + 強化訓練訊號 | 規則層已有（tool-output-trust 規則 1-5 + PC-166 A-F），不升級，改靠模型能力進步 | 規則層（現狀） | 已有——依賴模型進步 |

### R（Reality Test）— 方案可行性驗證

**方案 A 的侷限**：PostToolUse hook 注入的提示會進入 context，但 confabulation 的 L1 根因是「預期填補」——模型在高密度序列中傾向用預期分布填補，即使 system 提示說「你必須驗證」，模型仍可能在同一訊息「生成驗證命令 + 虛構其結果」（W5-011.3 已實證此路徑）。PostToolUse 提示是更強的「nudge」，不是 enforcement。

**方案 B 的價值**：事後審計無法預防，但有兩個價值：(1) 發現漏網案例建立 baseline（目前零可觀測性）；(2) 審計報告可回饋到規則層調整。Stop hook 現為 1 個（`continuous-learning`），可擴展。

**方案 C 的不可行性**：需 CC runtime 新增「tool_use 後 forced readback」機制，非本專案可控。可作為 CC feature request 提出但不能依賴。

**方案 D 的可行性**：以 `ticket track complete` 為例——complete 已在 CLI 內執行 status 變更，可在 CLI 層增加「complete 後自動 query 回 status 並附在 stdout」。模型收到的 tool_result 已含驗證數據，不需要額外發驗證命令。此方案對齊 opinionated-default 設計原則（主張 2：工具必須表達 opinion）。但僅限本專案 CLI 可控的 mutation，對 git commit 等外部工具無效。

### A（Attain distance）— 機會成本

實作方案 A+B+D 的開發成本：
- A（PostToolUse hook）：約 1 個 IMP ticket（mutation 偵測 + 提示注入）
- B（Stop hook 審計）：約 1-2 個 IMP ticket（transcript 解析 + git/ticket 狀態比對 + 報告格式）
- D（CLI self-verify）：約 1 個 IMP ticket per mutation CLI（complete / append-log / create 各一）

機會成本：佔用 W6 容量，擠壓多書城適配器（v1.5.0 主目標）進度。

### P（Prepare to be wrong）— 失敗預想

最可能失敗原因：**方案 A/D 在實務中不降低 confabulation 發生率。** 原因：confabulation 的 L1 根因是模型的自回歸生成行為，不是「缺乏驗證資訊」——W5-011.3 中模型收到的 tool_result 包含完整成功/失敗資訊，仍然虛構。增加更多驗證資訊不改變生成行為。

### 結論

**規則層為當前上限，hook 層無法實現真正的 confabulation enforcement。** 理由：

1. **根本限制**：confabulation 是模型文字生成行為，CC hook 系統只攔截工具呼叫，兩者不交叉。無 AssistantTextGeneration 事件。
2. **PostToolUse 是 nudge 非 enforcement**：注入驗證提示模型仍可忽略（W5-011.3 已實證驗證步驟自身被虛構）。
3. **Stop hook 事後審計有價值但不預防**：建議作為可觀測性改善（非 enforcement 升級）獨立評估。
4. **Opinionated CLI self-verify 是最務實的局部改善**：讓 mutation CLI 輸出自帶驗證數據，減少模型需要額外發驗證命令的場景，但僅限本專案 CLI。
5. **真正的 enforcement 需 CC runtime 支援**：「mutation 後 forced readback」需 CC 平台層改動，可作為 feature request。
