### 分析範圍與方法

**問題**：ticket 系統以 Linux process 模型設計（ticket=process 承載資訊、ticket ID=PID、派發 agent=多線程、以 ID 為記錄核心），使用數月後需以實證回顧設計缺失。

**證據基礎（三源）**：
1. 量化：2285 張歷史 ticket 語料庫全量 grep 普查（見重現實驗結果）
2. 質性：289 個 error-pattern（PC 200 + IMP 89）、數月累積的 memory feedback（約 90 條，其中 ticket 系統相關約 40 條）
3. 結構：ticket CLI（39 子命令）、25 個 ticket skill hooks、settings.json 80 註冊 hooks

**方法**：Linux process 模型逐項對照（成立處/斷裂處）→ 每項缺失錨定實證 → WRAP 檢核關鍵判讀 → 改進方向 spawn 規劃。

## Solution

### WRAP 檢核

**錨點**：流程決策——ticket 系統是框架骨幹，改善具持續回報；框架修改優先於專案進度（用戶既定原則）。
**Step 0**：資料充足（2285 票普查 + 289 error-pattern + 數月 memory）；已標記 4 項量測 caveat。
**W（假設層級多元）**：對「事故密度高」列 6 個候選根因假設——H1 單檔職責過載 / H2 寫入介面未收斂 / H3 類比對象錯位 / H4 枚舉無強制 / H5 三平面無單一事實來源 / H6 反向假設：非設計缺失而是 LLM agent 特性必然成本。方案性質三類涵蓋確認：改進方向含新增工具（D7）、改造既有（D1/D2/D4/D5）、零工具純文件（D8）與顯性不動（D6 拆檔豁免）。
**R（現實檢驗）**：基本率——成熟 tracker（Jira/Linear/GitHub）= DB + API 唯一寫入；OS kernel = 單一寫入者 + syscall；本系統 = 可自由 Edit 的平面檔案 + 事後 hook 驗證，屬離群設計。反向基本率——git-based tracker（git-bug/fossil）與 md-based PM 確實存在，以弱完整性換版本化與人類可讀性，故儲存選型可辯護，缺口在寫入紀律而非儲存介質。
**A（拉開距離 + Consider the Opposite 修正）**：初判「hook 增生 85 個是病」，反向思考後修正——hook 增生是規則 6（失敗案例學習）的制度化記憶，屬資產；真正的病是**同一類錯誤跨欄位重複發生**（枚舉漂移在 type/priority/status/章節名四處各自發生一次），表示缺的是一個寫入時驗證機制，而非 200 個事後 pattern。10/10/10：不修寫入邊界，hook 數與 PC 數將隨欄位數線性增生。
**P（準備犯錯）**：本分析最大風險 = 建議大改重寫一個運作中的系統（2190 completed、舊版 pending 歸零證明系統整體有效）。防護：所有改進方向設計為增量式、各自獨立可驗證、不含 big-bang 重構。次風險 = 普查為 grep 近似（caveat a-d 已標）。

### 二、設計缺失（F1-F9，每項附實證）

### F1【最高層級】類比對象錯位：ticket 是 batch job 不是 process；agent 是 thread 不是 process
- Linux process：fork 即繼承身份（UID）、位址空間預設隔離。
- 本系統實況：身份在 claim 時晚綁定（**17% completed 票身份從未回填**；who.current 預設字面 "pending" 引發 identity-guard deny 鏈 → W2-018 claim --as 補丁）；agent 預設共享 working tree（執行緒模型），隔離（worktree/feat branch）是 opt-in 且昂貴。
- 事故聚集正好在兩個預設反轉點：共享樹競態（PC-092 commit race、PC-137 並行 Edit deny、PM Edit 期間 agent 越界 commit）、worktree stale base（IMP-066）。
- 正確類比是 SLURM/k8s Job：submit/schedule/assign/execute 分離，身份在 assign 綁定，工作區預設隔離。系統演化實際上一直朝此方向補丁（claim --as、feat branch 三句 SOP、dispatch-active.json），但自我描述仍是 process 模型，導致每次補丁都被當個案而非模型修正。

### F2 單檔五職責融合（descriptor + context + journal + contract + audit）
- Linux PCB 是固定 schema 的 kernel struct；ticket md 是無界文件。
- 單一 write surface 由 PM/agent/hook 三方共寫 → auto-stage 同檔 merge conflict（W1-048.2）、body 未 commit 被 git 還原（W7-001 auto-commit 補丁的起因）、file-size guardian 37 檔超標。
- 反向 steelman（保留判斷）：對 LLM agent，單檔一次 Read 取得全上下文是**優勢**，PCB+address space 融合是 feature。故 F2 的解不是拆檔，是收斂寫入介面（見 D6 豁免）。

### F3【根因核心】無 kernel：寫入路徑未收斂，一致性靠事後 hook 免疫系統
- 枚舉漂移四處實證（同一類錯誤重複發生）：type 漂移 11 筆（test-design/INV/analysis...）、priority 漂移 17 筆（P9/P4/中/高）、spawned_tickets 漂移（「無」/inline）、章節名漂移 77 筆（測試結果/實作摘要/變更摘要...）。
- priority 無 CLI 命令 → 71% 停在預設 P2，排程器主排序鍵無人維護（F5 併入此因）。
- 上游剛確診同病：PC-MON-002「必填不等於有效——CLI 必填欄位無格式/存在性驗證」。
- Linux 對照：kernel 是唯一寫入者，invariant 由 syscall 邊界強制；本系統 CLI 只覆蓋部分欄位，直接 Edit frontmatter 可繞過一切。

### F4 依賴三重編碼：Wave 序 + When 散文 + blockedBy 彼此漂移
- blockedBy 空值率 86%（1960/2285），依賴實際藏在 Wave 編號與 When 散文。
- 已有實證：blockedBy CLI 滿足 ≠ When 語意前提滿足（memory feedback）；runqueue 的答案品質受限於 DAG 編碼覆蓋率。

### F6 記錄平面 vs 世界平面雙面帳（ticket status 是第三平面）
- ghost branch、並行 session race（W1-024）、agent 回報完成但 worktree 未合併（PC-039）、API 錯誤中斷但實質完成（W2-009.3）。
- 已固化為 tool-output-trust 規則 5，但 complete 時的 git ground truth 自動比對仍缺（現靠 PM 手動）。

### F7 深度與扇出的長尾失控
- 深度 4-5 層票計 23 筆（MAX_TICKET_DEPTH=3 僅 warning 且 W1-056.5 才補）；巨型父票 18/16/14/13 子。
- 對照 PC-042（subagent ~20 tool call）：資源限制（ulimit 對應物）是被動發現而非建票時主動檢查，dispatch-readiness 到 W17-053 才補。

### F8 協議演進無 schema 版本化，corpus 異質
- Exit Status/NeedsContext 僅覆蓋後期 60%、Context Bundle 33%、重現實驗結果為 ANA 的 86%。
- frontmatter 無 schema_version 欄位，每次工具鏈假設變更都需相容全歷史變體或靜默排除。

### F9 同名鍵跨層衝突（自證式發現）
