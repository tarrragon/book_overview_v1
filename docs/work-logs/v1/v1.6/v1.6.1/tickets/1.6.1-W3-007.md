## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

`attemptFallback` (L589) 與 `switchToPlatform` (L236) 之間存在無保護的互相遞迴呼叫：

**遞迴鏈**：`switchToPlatform` 失敗 → catch block L307-308 呼叫 `attemptFallback` → `attemptFallback` L597/L617 呼叫 `switchToPlatform` → 再次失敗 → 再次 `attemptFallback` → 無窮迴圈

**三個失效的防護點**：

| 防護點 | 現狀 | 應有行為 |
|--------|------|---------|
| `maxRetries: 3` (L62) | 已定義但從未在邏輯中使用（僅出現於日誌 L177） | 應作為遞迴深度上限 |
| `isFallback: true` (L599/L619) | `attemptFallback` 傳入此選項，但 `switchToPlatform` catch block (L307) 不檢查 | 應跳過二次 fallback |
| `concurrentLimit: 1` (L66) | 僅保護 L252 之後的路徑；驗證失敗 (L248) 在 L252 之前拋出，完全繞過並發保護 | N/A（設計目的非防遞迴） |

**直接原因**：L307-308 無條件觸發 fallback，不檢查 `options.isFallback`

### 影響範圍

**受影響檔案**：`src/background/domains/platform/services/platform-switcher-service.js`（單一檔案）

**受影響功能**：
- `switchToPlatform` (L236) — 所有平台切換操作
- `attemptFallback` (L589) — 故障轉移邏輯
- `handlePlatformError` (L766) — 嚴重錯誤自動 fallback 入口 (L777)

**已驗證的事實**：
1. `maxRetries` 在此檔案中僅 L62（定義）和 L177（日誌）出現，邏輯中零使用
2. 測試檔案 L54-57 已用 `autoFallback = false` 迴避此問題（開發時已知但未修復）
3. W3-004 SR-2 實測已觸發 heap OOM

**仍未驗證的假設**：
- heap OOM 觸發路徑是驗證失敗的純遞迴還是後設路徑的死鎖 promise 堆積，需 runtime 實測確認

### 相關 Error Pattern

無直接匹配的既有 error pattern。本問題屬實作缺陷（遞迴無終止條件），非流程或框架問題。

## 重現實驗結果
### 實驗方法

靜態呼叫鏈追蹤：逐行追蹤 `attemptFallback` ↔ `switchToPlatform` 的相互呼叫路徑，識別所有遞迴入口與終止條件（或缺失的終止條件）。

### 實驗執行

**路徑 1：驗證失敗導致的純無窮遞迴**（最危險，無任何保護）

```
switchToPlatform(B) 呼叫
  → L243: validateSwitchRequest(B) 失敗（如平台未註冊/非 active）
  → L248: throw error（注意：此時尚未到達 L252 enforceConcurrencyLimit，也未到 L259 activeSwitches.set）
  → L297: catch block
  → L308: attemptFallback(switchId)
    → L594: previousPlatform 存在時 → L597: switchToPlatform(previousPlatform)
      → 若 previousPlatform 也驗證失敗 → L248 throw → L308 attemptFallback → 無窮迴圈
    → L610: previousPlatform 為 null 時 → L614-631: 遍歷 activePlatforms
      → L617: switchToPlatform(platformX) → 若失敗 → 其 catch block L308 再次呼叫 attemptFallback
      → 每個失敗的 switchToPlatform 都觸發新的 attemptFallback → 指數級遞迴展開
```

**關鍵**：驗證失敗在 L248 拋出，早於 `enforceConcurrencyLimit` (L252) 和 `activeSwitches.set` (L259)，因此 `concurrentLimit` 保護完全被繞過。這是純無窮遞迴，無任何機制可阻止。

**路徑 2：後設失敗導致的死鎖**（concurrentLimit=1 時）

```
switchToPlatform(B) 呼叫
  → L252: enforceConcurrencyLimit 通過（activeSwitches.size=0 < 1）
  → L259: activeSwitches.set(switchId1)（size=1）
  → L276: executeSwitchProcess 失敗
  → L297: catch block（注意：activeSwitches 尚未刪除，在 finally L319 才刪）
  → L308: attemptFallback(switchId1)
    → L597: switchToPlatform(previousPlatform)
      → L252: enforceConcurrencyLimit（activeSwitches.size=1 >= concurrentLimit=1）→ 進入 queue
      → queue 等待 processQueuedSwitches 解鎖
      → processQueuedSwitches 在第一次 switchToPlatform 的 finally block (L323) 才呼叫
      → 但 finally 等待 catch block 中的 attemptFallback 完成
      → 死鎖：A 等 B 完成，B 等 A 的 finally 解鎖
```

**路徑 3：handlePlatformError 觸發的遞迴入口**

```
PLATFORM.ERROR.OCCURRED 事件（severity='critical'）
  → L770-773: 條件滿足（當前平台 + critical + autoFallback + 非 switching）
  → L777: attemptFallback('error-fallback-...')
  → 進入路徑 1 或路徑 2 的遞迴鏈
```

### 實驗發現

**已驗證的事實**：
1. 存在兩種故障模式：純無窮遞迴（路徑 1，驗證失敗繞過並發保護）和死鎖（路徑 2，並發保護導致 promise 懸掛）
2. `maxRetries=3` 是死程式碼——定義於 L62，日誌記錄於 L177，邏輯中零引用
3. `isFallback: true` 由 `attemptFallback` 傳入（L599/L619），但 `switchToPlatform` catch block (L307) 不檢查此選項
4. 測試已用 `autoFallback = false` 迴避（L57），等同屏蔽了整個 fallback 功能的測試覆蓋
5. `attemptFallback` 的 else 分支 (L614-631) 遍歷所有活躍平台，每個失敗的 `switchToPlatform` 都獨立觸發 `attemptFallback`，在所有平台皆失敗時造成指數級遞迴展開
6. 存在三個觸發入口：L308（switchToPlatform catch）、L777（handlePlatformError）、L723（handleSwitchRequest 間接觸發）

**仍未驗證的假設**：
- W3-004 SR-2 實測 heap OOM 的具體觸發路徑（路徑 1 vs 路徑 2）需 runtime profiling 確認
