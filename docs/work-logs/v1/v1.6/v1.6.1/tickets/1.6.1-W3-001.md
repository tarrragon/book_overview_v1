## Problem Analysis

### 問題根因

domain map 對齊分析發現 extraction domain 6 個 bundle 中，Extraction Coordinator / Data Processing / Extraction Validation / Quality Control 四個 bundle 缺乏 unit test 覆蓋，屬歷史測試債務。

### 影響範圍

`tests/unit/background/domains/extraction/` 目錄下新增 5 個測試檔（對應四個 bundle，Extraction Coordinator 拆為協調器本身 + State Service 兩檔，因兩者分別代表協調器生命週期與作業狀態機兩個可獨立驗證的介面）。未修改任何 `src/` 產品程式碼。

### 相關 Error Pattern

無。

---

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->

依 Context Bundle 不變式表新增以下測試檔：

- `extraction-domain-coordinator.test.js` — 協調器建構/初始化/生命週期（idle -> extracting -> completed 對應 initialize -> start -> stop）、五個微服務建立順序、服務存取介面、診斷報告
- `extraction-state-service.test.js` — 作業狀態機不變式：`createExtractionJob` 建立為 PENDING（idle）、`startExtractionJob` 轉為 RUNNING（extracting）、`completeExtractionJob` 轉為 COMPLETED 並移出 `extractionJobs` Map，驗證完成後無法直接重新 `startExtractionJob`（拋出「提取作業不存在」，即不可從 completed 直接回 extracting）、`failExtractionJob` 依 `maxAttempts` 分流 RETRYING/FAILED
- `data-processing-service.test.js` — `standard_book_processing` 管道固定順序 validate_input -> normalize_data(processor) -> clean_data -> enrich_data -> validate_output；快取命中時處理器（parse）不被重新呼叫，快取未命中（資料內容不同）則重新呼叫
- `validation-service.test.js` — `book_basic` 規則群組缺 id / 缺 title 時驗證失敗；`validateBatch` 回傳與輸入項目數量相同、各自獨立判定的結果陣列
- `quality-control-service.test.js` — `analyzeDataQuality` 整體分數落在 0-1（對應 ticket 描述的 0-100，實作為 0-1 分數）；`addQualityRule` 可覆寫既有規則之 threshold 驗證異常偵測閾值可配置；`calculateSeverity` 依偏差程度回傳 INFO/WARNING/CRITICAL
