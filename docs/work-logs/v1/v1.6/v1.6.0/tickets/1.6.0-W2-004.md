## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

現有 `docs/use-cases.md` 的 7 個 UC（UC-01 至 UC-07）全部以 Readmoo 單一書城為前提撰寫。v1.5.0+ 的多書城架構（PlatformRegistry + PlatformAdapterInterface + per-store storage key）已到位，但 UC 層未同步更新，導致 storage 覆蓋等問題在設計階段未被 UC 驗收條件捕捉。

### 影響範圍

- `docs/use-cases.md` 全部 7 個 UC 需補充多書城維度
- 可能需新增 2-3 個多書城專屬 UC
- 影響 TDD Phase 2 測試設計（測試案例以 UC 為基礎）

### 相關 Error Pattern

無直接相關 PC。動機來自 v1.5.0 實機暴露的 storage 覆蓋問題（1.6.0-W2-003 已處理 storage 隔離常數層）。

## 重現實驗結果
### 調查方法

逐一對照現有 7 個 UC 與 6 個多書城使用情境維度：

| 維度 | 說明 |
|------|------|
| 提取隔離 | 不同書城資料分開儲存（`{platformId}_books` key） |
| 合併顯示 | Overview/Popup 顯示所有書城的合併書目 |
| 多書城匯出/匯入 | 匯出含 source 欄位、匯入路由至正確書城 key |
| 書城偵測切換 | Extension 偵測當前網站載入對應 adapter |
| 跨書城去重 | 同一本書在不同書城的識別與處理 |
| 錯誤隔離 | 單一書城錯誤不影響其他書城功能 |

### 調查結果：逐 UC 缺漏清單

**UC-01 首次安裝與設定**
- 缺漏 G1: 前提僅寫「Readmoo 書庫頁面」，無「首次造訪新書城」的流程
- 缺漏 G2: 無書城自動偵測 UX（Extension 如何讓用戶知道「已偵測到 Kobo」）
- 缺漏 G3: 無多書城首次 storage 初始化描述
- 嚴重度：高（書城偵測切換維度完全空白）

**UC-02 日常提取**
- 缺漏 G4: 提取流程假設單一書城，無 per-store storage 寫入路徑
- 缺漏 G5: 去重僅在同書城內，無跨書城去重場景（同書兩個書城皆有）
- 缺漏 G6: 無「在 Kobo 頁面提取但 Readmoo 資料不受影響」的隔離保證
- 缺漏 G7: 成功訊息「新增 X 本」未標示書城來源
- 嚴重度：高（提取隔離維度完全空白）

**UC-03 匯出與備份**
- 缺漏 G8: 檔名 `readmoo-books-YYYY-MM-DD.json` 硬編碼 Readmoo
- 缺漏 G9: 無「匯出全部書城合併」vs「匯出單一書城」的選項流程
- 缺漏 G10: CSV 匯出未含 `source` 欄位（SPEC-STORAGE-ISOLATION D4 已定義）
- 缺漏 G11: 匯出時合併讀取路徑 `loadAllPlatformBooks()` 無 UC 描述
- 嚴重度：中（架構已規劃但 UC 未對齊）

**UC-04 匯入與恢復**
- 缺漏 G12: 匯入檔案含多書城 source 時的路由邏輯無 UC 描述
- 缺漏 G13: 匯入單一書城資料（如 Kobo 備份）寫入正確 key 的驗收條件缺失
- 缺漏 G14: 合併模式下跨書城 tag 聯集策略未更新（tag 含 source context）
- 嚴重度：中

**UC-05 跨設備同步**
- 缺漏 G15: 同步資料包含多書城時，兩端書城清單不一致的處理
- 缺漏 G16: 設備 A 有 Readmoo+Kobo，設備 B 僅有 Readmoo 的 partial sync
- 缺漏 G17: 同步格式（canonical）需包含 source 欄位以保留書城歸屬
- 嚴重度：中

**UC-06 檢視與管理**
- 缺漏 G18: 無「按書城來源篩選」的篩選選項
- 缺漏 G19: 合併顯示時同一本書跨書城的標示方式
- 缺漏 G20: 書籍清單需顯示書城來源圖示/標籤
- 缺漏 G21: 清除資料時「清除單一書城」vs「清除全部」
- 嚴重度：高（合併顯示維度完全空白）

**UC-07 錯誤處理**
- 缺漏 G22: 無「單一書城 DOM 結構變更不影響其他書城」的錯誤隔離場景
- 缺漏 G23: 無「未登入特定書城」的錯誤場景（用戶在 Kobo 頁面但未登入）
- 缺漏 G24: 無「部分書城提取成功、部分失敗」的部分成功場景
- 缺漏 G25: 無「書城地區限制」錯誤場景（如 Kindle JP vs US）
- 嚴重度：高（錯誤隔離維度完全空白）

### 新增 UC 候選

| 新 UC ID | 名稱 | 理由 |
|---------|------|------|
| UC-MP-01 | 多書城偵測與切換 | 書城自動偵測、adapter 載入、用戶通知為全新使用情境，無法自然融入現有 UC |
| UC-MP-02 | 跨書城書庫合併檢視 | 合併顯示、來源篩選、跨書城去重為獨立使用情境 |
| UC-MP-03 | 單一書城資料管理 | 書城級清除、書城級匯出、書城啟用/停用 |

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 分析結論

25 個缺漏（G1-G25）+ 3 個新 UC 候選。按嚴重度與版本規劃建議處理方式：

### 處理策略

#### 策略 A：現有 UC 增補多書城維度（G1-G25）

對現有 7 個 UC 各新增「多書城影響」章節（與 v1.1 的 Tag-based Model 影響章節同結構），描述多書城場景下的變更。這是最小改動方式，保持 UC 文件結構穩定。

#### 策略 B：新增獨立多書城 UC（UC-MP-01~03）

| UC | 落地版本建議 | 理由 |
|-----|-----------|------|
| UC-MP-01 多書城偵測與切換 | v1.5.0（第一個非 Readmoo 書城） | 書城偵測是 adapter 開發的前提流程 |
| UC-MP-02 跨書城合併檢視 | v2.0.0（多書城統一管理） | 合併檢視需所有書城 adapter 就位後才有意義 |
| UC-MP-03 單一書城資料管理 | v2.0.0 | 書城級操作是高階管理功能 |

#### 策略 C：版本分期

| 版本 | 應完成的 UC 更新 |
|------|----------------|
| v1.5.0 | UC-01/02/07 增補多書城維度（提取隔離 + 偵測切換 + 錯誤隔離）+ 新增 UC-MP-01 |
| v1.6.0-v1.11.0 | UC-03/04 增補多書城維度（匯出入路由）|
| v2.0.0 | UC-05/06 增補 + 新增 UC-MP-02/03（合併顯示 + 書城管理）|

### Spawn 規劃

| 類型 | What | Why | Priority |
|------|------|-----|----------|
| DOC | UC-01/02/07 多書城維度增補（v1.5.0 scope） | 第一個非 Readmoo 書城上線前需 UC 規格對齊 | P1 |
| DOC | 新增 UC-MP-01 多書城偵測與切換 | v1.5.0 核心新 UC | P1 |
| DOC | UC-03/04 多書城維度增補（v1.6.0+ scope） | 匯出入需 source 路由 | P2 |
| DOC | UC-05/06 + UC-MP-02/03（v2.0.0 scope） | 合併管理為 v2.0.0 功能 | P2 |

### 與 SPEC-STORAGE-ISOLATION 的對齊確認

Storage 隔離規格（D1-D5）已定義技術實作，但 UC 層（用戶視角）尚未對齊：
- D1 Storage Key 命名 → 需反映在 UC-02 提取流程
- D4 匯出 source 欄位 → 需反映在 UC-03 匯出流程
- D3 合併讀取 → 需反映在 UC-06 合併顯示
