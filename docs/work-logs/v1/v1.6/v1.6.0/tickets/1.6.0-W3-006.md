## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

專案存在兩套獨立的 UC 文件系統，編號各自獨立但 UC ID 命名空間重疊：
1. `docs/use-cases.md`（舊版單檔）：Extension 專屬 UC-01~07，無 YAML frontmatter
2. `docs/usecases/`（新版目錄）：跨平台 UC-01~09，有結構化 frontmatter + platform 欄位

### 影響範圍

新增多書城 UC 時，不知該放哪套、用哪套的編號序列。

### 相關 Error Pattern

無。

## 重現實驗結果
### 調查方法

直接盤點兩套 UC 系統的編號、名稱、平台歸屬和格式。

### 實驗發現（已驗證事實）

1. 兩套系統的 UC ID **完全不同義**：舊版 UC-01=安裝設定，新版 UC-01=匯入；舊版 UC-03=匯出，新版 UC-02=匯出
2. 新版（`docs/usecases/`）有結構化 frontmatter、platform 欄位、Extension 狀態追蹤，設計更完整
3. 新版已有 UC-09（chrome-extension 專屬），證明新版系統支援 Extension-only UC
4. 舊版已累積 v1.1 tag-based 影響 + 本 session 的 v1.5+ 多書城影響章節，內容仍在維護
5. `docs/usecases/README.md` 已宣告「原始用例文件：`../app-use-cases.md`（保留為歷史參考）」，但未宣告 `docs/use-cases.md` 的定位

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 分析結論

#### 候選方案

| 方案 | 說明 | 優點 | 缺點 |
|------|------|------|------|
| A. 統一到 docs/usecases/ | 新多書城 UC 建在 docs/usecases/ 接續 UC-10/11/12；docs/use-cases.md 標為 legacy 參考 | 單一命名空間、結構化 frontmatter、支援 platform 標記 | 需決定舊版 7 個 UC 的遷移時機 |
| B. 兩套並行各編各的 | docs/use-cases.md 用 UC-08/09/10，docs/usecases/ 用 UC-10/11/12 | 無遷移成本 | 永久分裂、同 ID 不同義混淆持續 |
| C. 合併後統一重編 | 兩套合併為一套，所有 UC 重新編號 | 完全乾淨 | 成本極高，已有引用全部需更新 |

#### 建議：方案 A — 統一到 docs/usecases/

理由：
1. docs/usecases/ 是較新的設計，有 platform 欄位可區分 extension/app/both
2. UC-09 已證明 extension-only UC 可自然融入 docs/usecases/
3. 新多書城 UC 從 UC-10 開始，避免任何編號衝突
4. docs/use-cases.md 標為 legacy reference（不刪除、不再新增 UC），已有的 v1.1/v1.3 增補內容遷移時整合到 docs/usecases/ 對應 UC

#### 命名規則

新多書城 UC 編號方式：

| 原 W2-004 候選 | 統一後 UC ID | 檔案 |
|---------------|------------|------|
| UC-MP-01 多書城偵測與切換 | UC-10 | `docs/usecases/UC-10-multi-platform-detection.md` |
| UC-MP-02 跨書城合併檢視 | UC-11 | `docs/usecases/UC-11-cross-platform-merged-view.md` |
| UC-MP-03 單一書城資料管理 | UC-12 | `docs/usecases/UC-12-single-platform-management.md` |

#### 過渡期安排

- docs/use-cases.md 開頭加 legacy notice，指向 docs/usecases/
- 新 UC 一律建在 docs/usecases/（UC-10+）
- 舊版 7 個 UC 的內容遷移不在本 ticket 範圍，如需要可另建 DOC ticket
