## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### Context Bundle

**介面定義（Phase 1 規格）**：見父 ticket 1.6.0-W3-001 Solution「Background Fetch Message Protocol」章節

**修改目標**：`src/background/messaging/content-message-handler.js`
- 新增 `CONTENT.FETCH.PAGE_HTML` 到 `supportedMessageTypes`
- 新增 `handleFetchPageHtml()` 方法
- 在 `routeContentMessage()` 加入 case 路由

**安全約束**：
- handler 驗證 URL hostname 屬已知平台域名（kobo.com 等）
- 域名白名單可從 PlatformRegistry 或硬編碼常數取得
- 超時 30 秒
- 回應格式：`{ success, html?, error?, status? }`

**WRAP 三問**：
- W: 候選方案 (a) 在 ContentMessageHandler 內新增 handler（chosen，與既有 message 路由一致）(b) 獨立新建 FetchProxyHandler 類（過度設計，目前僅此一用途）
- A: 無擠壓——.1 是 .2 的前置依賴，必須先做
- P: 最可能失敗原因：Chrome Extension SW 環境的 fetch API 限制（如 cookies 傳遞）；防護：測試驗證 credentials: 'include' 行為

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
在 `src/background/messaging/content-message-handler.js` 新增 `CONTENT.FETCH.PAGE_HTML` 訊息類型支援：
- `supportedMessageTypes` 新增類型；`routeContentMessage()` 新增對應 case
- 新增 `handleFetchPageHtml()`：驗證 url 必填 → `new URL()` 解析格式 → `isAllowedFetchDomain()` 域名白名單檢查（hostname 精確或子域名比對，防尾碼偽裝）→ `AbortController` 30 秒逾時 fetch（`credentials: 'include'`）→ 依 `response.ok` 回傳 `{success, html, status}` 或 `{success:false, error, status}`
- 域名白名單 `ALLOWED_FETCH_DOMAINS = ['kobo.com', 'books.com.tw', 'readmoo.com']` 為模組內硬編碼常數（依 ticket Context Bundle 指示，跨書城通用，非 UI 常數不進 design-system）
