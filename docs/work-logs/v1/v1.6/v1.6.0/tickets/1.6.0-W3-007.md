## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 用戶補充設計方向

多書城場景下，書目 ID 不應依賴各書城原始 ID（不同書城 ID 體系不同，可能為 null）。正確做法：

- **書目 ID**：由系統自行生成（如 UUID），作為唯一識別符
- **書城原始 ID**：作為備用欄位記錄（如 `platformBookId`），供回查書城用

### 初步根因分析

Overview `_getBookId(book)` 依賴 `book.id || book.bookId`（overview-page-controller.js:428-431）。
部分書目兩欄位皆為 falsy，導致 checkbox 不渲染（L813 `if (bookId)` 不通過）。
截圖顯示約 3/8 本書缺少 checkbox，比例不低。

### 跨專案影響（用戶補充）

書目來源不只書城提取，還有 APP 端掃描建立。兩個專案（Chrome Extension + Flutter APP）都必須自建 ID：

- **Chrome Extension**：從書城提取的書目
- **Flutter APP**：用戶手動掃描（ISBN barcode）建立的書目

兩端產生的書目最終會透過同步機制交換，ID 體系必須統一。此問題影響範圍跨 V1（Extension）和 V2（APP）兩個專案。
### ISBN 不適合作唯一 ID（用戶補充）

ISBN 會因再版或重新出版而變動，但在用戶認知中仍是「同一本書」。系統已支援將多本書（不同 ISBN/不同版本）歸類到同一本書底下。

因此 ID 策略需考慮三層結構：

| 層級 | 含義 | 範例 |
|------|------|------|
| 書目 ID（自建） | 系統內唯一識別符 | UUID v4 |
| 書城原始 ID | 各書城平台的商品 ID | platformBookId |
| ISBN | 出版識別碼，同一本書可能有多個 | 再版/重出版/不同格式 |

關鍵約束：同一本「邏輯書」可對應多個 ISBN、多個書城商品、多個書目記錄。系統已有「歸類到同一本書」的功能支援這個合併語意。ID 生成策略不能用 ISBN 作為 natural key 去重——去重應在更高的「邏輯書」層級處理。
## 重現實驗結果
### 實驗方法

以靜態程式碼分析追蹤資料流：adapter 提取 → event-coordinator 正規化 → Chrome Storage 儲存 → overview 載入 → checkbox 渲染。

### 實驗執行

**步驟 1：追蹤 `_getBookId()` 與 checkbox 渲染邏輯**

`overview-page-controller.js:428-431`：
```js
_getBookId (book) {
    if (!book) return null
    return book.id || book.bookId || null
}
```

`overview-page-controller.js:810-828`：`if (bookId)` 為 falsy 時不建立 checkbox DOM 元素。

**步驟 2：各 adapter 的 ID 欄位名稱盤點**

| Adapter | 提取路徑 | ID 欄位名 | ID 來源 |
|---------|---------|----------|--------|
| readmoo-adapter | `extractBookData()` L496 | `id` | `generateStableBookIdWithInfo()` 4 策略 cascade（reader/cover/title/fallback），fallback 保證 truthy |
| kobo-adapter | `parseBookElement()` L222 | `bookId` | `_extractBookId(element)` — 從 DOM 提取 |
| books-com-tw API | `_mapApiRecordToBookData()` L375 | `bookId` | `info.item`（可能為空字串 `''`） |
| books-com-tw DOM | `parseBookElement()` L230-236 | **無 ID 欄位** | 未設計 — 完全缺失 |

**步驟 3：儲存層驗證缺口**

- `event-coordinator.js:556-574`：正規化只做 tags/readingStatus/applyDefaults，**不映射 `bookId` → `id`**，**不自動生成 `id`**
- `BookSchemaV2.applyDefaults()` L108-118：只補有 `default` 的欄位；`id` 定義為 `required: true` 但**無 `default`**，不會被補上
- `event-coordinator.js:589`：`chrome.storage.local.set()` **不呼叫 `validateBook()`**，無 ID 的書目直接存入
- `storage-save-handler.js:205`：有 `validateBooksStructure` 檢查 `book.id`，但 event-coordinator 未呼叫此 handler

**步驟 4：Overview 載入範圍**

- `overview-page-controller.js:510`：`chrome.storage.local.get(['readmoo_books'])` — **只讀 Readmoo**
- `loadAllPlatformBooks()` 存在於 `multi-platform-storage.js` 但 overview **未使用**
- L286：storage change listener 也只監聽 `changes.readmoo_books`

**步驟 5：遷移對無 ID 書目的處理**

- `cover-to-reader.js:180-182`：`if (!book.id)` → 跳過（logged but not fixed）
- `v1-to-v2.js:201-203`：`if (!book.id)` → 跳過（同上）
- 遷移不補 ID，只丟棄無 ID 書目

### 實驗發現

**已驗證事實**：

1. 各 adapter ID 欄位名稱不統一（`id` / `bookId` / 無），是結構性問題
2. 正規化層（event-coordinator）不做 `bookId → id` 映射也不自動生成 `id`
3. 儲存時不做 BookSchemaV2 驗證，無 ID 書目可直接存入
4. Overview 只載入 `readmoo_books`，多書城書目不可見
5. 遷移邏輯對無 ID 書目採「丟棄」策略
6. Readmoo 的 stable-id-generator 有 fallback（`'reader-undefined'`），新提取書目理論上必有 `id`
7. `_getBookId()` 已考慮 `book.id || book.bookId` 兩種命名，但無法處理「兩者皆空」

**仍未驗證假設**：

- 用戶截圖中 3/8 無 checkbox 書目的實際 storage 資料結構未確認（需實機檢查）
- 歷史 Readmoo 資料（stable-id-generator 實裝前）是否殘留無 ID 書目未確認
- 匯入功能（json-importer）匯入的書目是否可能缺 ID 未確認
